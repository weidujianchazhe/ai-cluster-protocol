# 11 · 因果标注与协作图

> worker 之间**唯一**的横向信息流：声明的、单向的、可审计的。

## 一、它解决什么问题

没有它的时候：

- C 能看到 B 的产出，但**看不到 B 受谁影响**；
- 审计方只能验证「这个产物对不对」，不能问「这个产物和 A 的方案是什么关系」；
- 「多智能体协作」的耦合在哪、密度多少、有没有价值——**全都看不见**。

有了它之后，每条证据可以声明：

```json
"contextRefs": [
  { "nodeId": "ARCH", "how": "读了 ARCH 的接口定义，按它实现了调用" }
]
```

## 二、为什么它不破坏任何现有性质

| 性质 | 为什么不受影响 |
|---|---|
| **可复现** | 只是记录，不改变执行顺序；同样的历史回放出同样的图 |
| **审计独立** | 引用是生产者填的，审计方**不需要**读被引用节点就能审当前节点 |
| **成本线性** | 不增加任何 LLM 调用；`how` 是自由文本，不强制写 |
| **fail-closed** | 声明错误（引用不存在的节点、自引用）**直接拒**，不静默接受 |

关键：**它不是通信，是标注**。被引用的节点不知道谁读了它，两边也没有任何等待关系。

## 三、三条校验，只拦明确错误

| 判据 | 为什么拦 |
|---|---|
| 被引用节点**必须存在** | 引用了图里没有的节点 = 拼写错误或幻觉 |
| **不能引用自己** | 自引用会造成假的耦合度 |
| 被引用节点**不要求已 done** | 参考「进行中节点」是真实协作，只是风险高；强制 done 会把这类排除掉。它的状态会在图里显示（`toStatusAtRead`）供人判断 |

**不校验**的部分：`how` 文本内容、`evidenceId` 是否真属于那个节点。

理由是**不做过度校验**——这一层是「声明」，不是「证明」；证明留给将来的产物引用检查。

**去重**：同节点引用两次只算一条边，避免耦合度虚高。

## 四、协作图输出什么

```json
{
  "edges": [{ "from": "BUILD", "to": "ARCH", "how": "…", "toStatusAtRead": "done" }],
  "nodes": [{ "nodeId": "BUILD", "inbound": 0, "outbound": 1, "island": false,
              "qualityScore": 83, "qualityGrade": "good" }],
  "totals": { "nodes": 9, "islands": 4, "edges": 5, "coupled": 5, "density": 0.07 },
  "quality": {
    "coupled":  { "nodes": 5, "avgScore": 100 },
    "isolated": { "nodes": 4, "avgScore": 81 },
    "delta": 19,
    "verdict": "有耦合的节点平均分高 19 分（100 vs 81）。**这是相关性，不是因果**…"
  },
  "hubs": [{ "nodeId": "ARCH", "inbound": 4 }]
}
```

四个看点：

| 字段 | 回答 |
|---|---|
| `island` | 哪些节点是孤岛（既不引用别人也不被引用） |
| `hubs` | 谁是信息枢纽（被引用最多） |
| `density` | 耦合密度（实际边 / 可能边） |
| **`quality.delta`** | **有耦合 vs 无耦合的平均质量分差** |

## 五、`quality.delta` 是唯一能回答「协作有没有用」的东西

这是 ① 和 ② 结合起来的产物：

```
① quality_report  →  单节点质量分
② collaboration_map →  谁读了谁
                     ↓
               有耦合的节点，质量是不是更好？
```

**但它的结论受三条约束，缺一条就会变成误导：**

### ① 样本不足时 `delta = null`

少于 `minSample`（默认 3，两侧各算）时不给数字，`verdict` 明确写：

> 样本不足，不下结论（有耦合且有分数 2 个 / 无耦合且有分数 1 个，各需 ≥3 个）。这是刻意的：给一个样本不足的数字，会被当成结论用。

### ② 有值时必须声明「相关性不是因果」

> 有耦合的节点平均分高 19 分（100 vs 81）。**这是相关性，不是因果**——可能是高能力节点更容易引用别人，而不是引用让别人做得更好。

### ③ `delta = 0` 时说「没有差异」，不硬凑结论

> 两侧平均分相同（100），耦合目前没有可观测的质量差异。

## 六、它是「耦合声明图」，不是「事实依赖图」

`contextRefs` 由**生产者自己填**，没有机制验证产物真的引用了对方。

所以读到一张漂亮的协作图时，要记得：**它证明的是"这些节点声称读了谁"，不是"这些节点确实用了谁的成果"**。

这个边界写在输出的 `note` 字段里。要跨越它需要下一步：**检查产物里是否真的出现了被引用节点的标识**（产物引用校验）。本版没做。

## 七、怎么用

```text
collaboration_map()                    # 默认 minSample=3
collaboration_map({ minSample: 5 })    # 更严格的样本门槛
```

写入侧：`evidence_submit({ ..., contextRefs: [{ nodeId, evidenceId?, how? }] })`

**权限**：`collab.read` 给全部 9 个角色（纯只读聚合）。

## 八、这一层做完之后，多智能体协作能力上升了吗

**上升了，但上升的是「可观测的协作」，不是「自动变强的协作」。**

准确说：

| 变化 | 是/否 |
|---|---|
| worker 之间能实时通信了 | ❌ 没有 |
| 节点会因为别人的状态改变行为 | ❌ 没有 |
| **能看见谁参考了谁、谁被孤立** | ✅ 有了 |
| **能量化"有耦合的节点是否更好"** | ✅ 有了 |
| **能发现"某节点声称读了 A，但 A 根本不存在"** | ✅ 有了（提交时拒） |

所以现在能做的判断是：**跑一批节点 → 看孤岛比例和 delta → 决定要不要继续加耦合**。

这就是为什么 ① 必须在 ② 前面：没有质量分，协作图只能告诉你"谁连着谁"，不能告诉你"连着的更好还是更差"。
