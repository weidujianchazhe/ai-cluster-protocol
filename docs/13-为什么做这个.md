# 13 · 为什么做这个

> 不是功能说明，是**踩坑记录**：我遇到什么、试过什么、为什么最后长成现在这样。
> 读它能省你重复踩一遍。

## 一、最初的坑：单个 agent 做不了大工程

一开始的想法很朴素：把需求写清楚，让一个 agent 从头做到尾。

**第一个撞墙的地方是上下文。**

一个中型工程（比如"把这个协议实现成插件，含测试和文档"）需要：
- 读几十个现有文件才能改对
- 记住已经改过什么、还没改什么
- 在几十处之间保持一致性

而这些**全挤在一个上下文里**。跑到一半，前面的细节开始模糊；再往后，为了省上下文，自己把关键信息压缩掉——然后就改错了。

**换更大的上下文也没有根本解决。** 因为问题不只是"装不下"，还有：

| 症状 | 本质 |
|---|---|
| 改到第 30 个文件时忘了第 3 个文件长什么样 | 上下文是**线性**的，但工程是**图**的 |
| 同一个 bug 修了两遍，第二次是因为忘了第一次 | 没有**持久记录** |
| 越到后面越保守，不敢动 | 因为不确定前面改了什么 |
| 出错后只能从头再来 | 没有**可回放**的中间态 |

## 二、试过错的做法

**① 堆 prompt**

把所有要求写进一个超长 prompt。结果：前 20% 认真执行，中间开始走样，最后开始编。

**② 分步走，人工衔接**

我自己拆步骤、每步喂给 agent。能跑通，但**每步的产物和上下一步的关系全靠我脑子里记**——我成了瓶颈。

**③ 多开几个 agent 并行**

看着很爽，结果是：**它们互相不知道对方在干什么**，改同一个文件、装同一个依赖、覆盖同一个配置。收尾时发现三份互相矛盾的实现。

**共同的问题**：这三种做法都是"**靠人脑维持一致性**"。人脑撑不住几十步。

## 三、真正的转折：把"一致性"从人脑搬到日志

现在这套东西的核心决定只有一个：

> **所有状态都是事件日志折叠出来的，没有第二份真相。**

具体说，节点、依赖、租约、证据、阶段闸门——全部由 `journal` 里的事件算出。日志是哈希链的（`seq` / `prevHash` / `hash` 逐条相接）。

这一步带来三个当时没想到的好处：

**① 出错时知道错在哪一步**

链一断立刻报 `STATE_HASH_BREAK` / `STATE_SEQ_GAP`，不给"看起来正常"的中间态。**失败是响亮的**。

**② 重启不用从头来**

从 journal 重建状态。快照只是加速器，锚点校验失败就退回重放——**快照坏了不影响正确性**。

**③ 可以问"当时为什么这么做"**

每一步都有记录，包括谁领的、什么时候过期的、证据是谁交的、谁审的。

## 四、第二个决定：审计方不能是生产方

这是被坑出来的。

早期我对"AI 说自己做完了"这件事**照单全收**。后来发现：它会说"已完成"，但产物里有个字段拼错了；它会说"测试通过"，但测试根本没跑。

**所以加了结构性约束**：

- 生产方交证据，**审计方必须是另一个实例**（`producer_instance ≠ auditor_instance`）；
- 证据有**来源分级**：`verified`（机器核验过）/ `inferred`（推断）/ `assumed`（假设）；
- **只有 `verified` 能撑起 `done`**，其他的只能进 journal 供人读。

这条约束不依赖"AI 是否诚实"，而是**结构上不给你自己给自己签字的机会**。

## 五、第三个决定：派发不做成"聪明的调度器"

最诱人的设计是：让一个"调度 Agent"看着全局，决定派谁干什么。

**没做**，理由很实际：

> 调度 Agent 本身也是 LLM。它会看错、会忘、会编。**一旦调度错了，整个图的执行就错了，而且不可回放**——因为你没法复现"当时的判断"。

所以派发是**确定性决策**：`deps` 全 `done` → 变 `ready` → 按配额派。同样的日志回放出同样的派发顺序。

**这个决定牺牲了"智能调度"，换来了可复现。** 后来验证是值的：调 bug 时能精确重放。

## 六、代价从来没藏着

这套东西**不便宜**：

- 每个子 agent 都是完整模型调用 + 独立上下文；
- 并行是 `maxParallel × 每轮上下文` 的**线性放大**；
- 1000 个节点在默认感知配置下要多花 60–80 万 token。

**它换来的不是"更快更省"，是"能做完原本做不完的工程"。**

这也是为什么文档里反复写"很耗 token"——不是免责声明，是**这个设计的固有成本**。

## 七、一个至今没解决的判断：这些编排有没有用

我们做了三样东西来"看见"：

| 工具 | 看什么 |
|---|---|
| `quality_report` | 单个节点的过程质量（证据来源 / 业务返工 / 审计独立性） |
| `collaboration_map` | 谁读了谁、有耦合的节点质量是不是更好 |
| `neighbor_digest` | 节点能看到上下游已完成产物的摘要 |
| `organization_review` | 组织层面的问题：集成契约卡在谁、冲突路由给谁、谁和谁撞写域 |

**但"协作有没有用"这个问题，现在还没有答案。**

因为样本不够：图上每个阶段只有 1–2 个节点，`delta` 永远算不出来。要回答它，得造一个 fan-in 差异明显的漏斗图，跑真实 worker。

**这一条还开着。** 写在这里是为了提醒自己：**工具做完 ≠ 结论成立**。

## 八、边界：到不了的地方

最后说清做不到什么：

| 层 | 能否触及 |
|---|---|
| token → 专家路由（模型内部） | ❌ |
| 上下文窗口内的推理 | ❌ 只能通过 prompt 间接影响 |
| **会话之间怎么分工** | ✅ 这就是本协议干的 |
| **会话之间怎么传信息** | ✅ journal / evidence / `contextRefs` |

**这套编排全部作用在"会话之间"。** 它不会让单次推理更强，也不会省算力。

组织能力（[15](14-组织因子与协调闭环设计.md)）也在这条线内：它能生成协调节点、把冲突路由给有能力的实例，但**它自己不做语义裁决**——"两个接口到底谁对"仍由专门的审计节点或人判。加组织能力会抬高协调、审计和返工成本，它不是性能优化。

详细的推演（以及「能否内化成模型内部 MoE」的猜想）在 [A1 MoE 专家编排猜想](A1-MoE专家编排猜想.md)。

## 拿去用的三条

如果你也在做类似的事，这三条最省时间：

1. **别指望 AI 诚实**，给它结构性约束：独立审计、证据分级、只有 verified 能进 done；
2. **别让 LLM 做调度**，除非你能接受不可回放——确定性派发换来的可复现性，调试时值回票价；
3. **先把日志做对**，再谈并行。没有可回放的单一事实源，并行只会让错误互相覆盖。
