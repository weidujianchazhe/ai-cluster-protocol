# 03 · 租约与 fencing

> 谁在做这个节点、做到一半怎么办、过期了会怎样。

## 一、租约不是锁，是能力凭证

`task_claim` 发出的租约：

```ts
{ node_id, owner, fencing_token, expires_at, heartbeat_at }
```

关键设计：**`fencing_token` 单调递增，且不绑定智能体身份**。

| 特性 | 含义 |
|---|---|
| 任一载体持当前 token 即可续租/提交 | 换载体（换 session、换实例）也能接手 |
| 旧 token 立刻失效 | `assertFencing` 拒绝过期 token，防止「复活的老 worker」写脏数据 |
| 续租失败 = 停手信号 | 不是「稍后重试」 |
| 过期不会被悄悄续成新 token | 必须先 `expire` 或 `takeover` —— **这条是故意保留的** |

## 二、TTL 的两个尺度

| 场景 | TTL | 为什么 |
|---|---|---|
| **生产期** | 默认 **60 s** | 快速失败。worker 崩了，60 秒内别人就能接手 |
| **审计期** | 默认 **600 s**（`auditLeaseTtlSec`） | `verify_done` 要求活租约，而一轮真审计要复核哈希、复算数值，**很容易超过 60 s** |

### 为什么审计态要单独延长

缺口是这样的，而且**谁都补不上**：

- `verify_done` 要求**活租约**；
- worker 提交证据后通常就**不再心跳**了；
- **审计方没有 fencingToken**（token 属于生产者），想续也续不了。

于是：证据一提交 → 租约 60 s 后到期 → 审计还没做完 → 节点卡在 `submitted`。

**做法**：证据落账的那一刻，由**系统**把租约延到审计窗口（`extendForAudit`），不指望谁去心跳。

四条性质：

| 性质 | 说明 |
|---|---|
| 只延长不缩短 | `Math.max` 语义；已更宽则连事件都不写 |
| `0` = 关闭 | 可显式退出该行为 |
| 留痕 | `lease_audit_extended`（含 `ttl_sec` / `fencing_token`） |
| **仍会过期** | 审计一直不来时，下面的两层修复会把它驳回 ready——**延长不制造新的永久卡死** |

## 三、过期回收：两层修复

### 第一层：`expire()` 补 `submitted` 分支

原来只把 `claimed/running` 送回 ready，`submitted` 走**空分支**。后果是**三路全关**：

| 出口 | 为什么不可达 |
|---|---|
| `task_claim` | 要求 `ready` |
| `verify_done` | 要求**活租约**（已删） |
| `rejectNode`（唯一驳回出口） | 只在 `verifyDone` 的 `credential-unavailable` 分支调用，而它在 `assertFencing` **之后** → 永远不可达 |

于是节点**永久卡死**：不能领、不能验、不能驳。

修法：`expire()` 增加 `submitted|verifying` 分支，走**既有的** `rejectNode`（ready + dropLease + `attempts+1` + `rejected:` 留痕），不新造状态迁移。

### 第二层：孤儿清扫

第一层只修了一半。因为 `expire()` 的遍历源是 `store.state.leases` ——**只有还存在租约的节点才会被看到**。

所以「租约早被删掉、节点却留在 `submitted`」的**孤儿**永远进不了循环。

线上真实积了 **7 个**孤儿（`MEASURE-01 / M8-01 / M8-03 / M8-04 / M8-05 / M8-06 / M8-07`）。

修法：`reapExpiredLeases()` 加第二遍清扫，判据只有一条事实：

```
状态 ∈ {submitted, verifying}  ∧  该节点没有租约  →  rejectNode(..., 'orphan_submitted')
```

**有租约的一律不碰**——租约是权威存活证明，正在验的节点不能被误驳。

## 四、为什么这个坑值得单独记

这是**同一形态第 N 次出现**：某条路径的**前提**在另一条路径里被悄悄破坏。

| 出现 | 形态 |
|---|---|
| 第一次 | 审计身份被解析成 producer → 合法审计永远被拒（见 [04](04-证据与审计.md)） |
| 第二次 | `expire()` 跳过 `submitted` → 三路全关 |
| 第三次 | 测试的窗口假设被新行为改掉（加了审计延长后，`ttlSec:1` 的断言挂了） |

**共同点**：都不是性能或配置问题，而是**某个前提在别处被改掉了，而依赖它的地方不知道**。而且**只有真派 Agent 才会暴露**——模拟 worker 绕开了这些路径。

## 五、孤儿清扫的可观测性

清扫必须**单独报出来**，不能和「过期租约」混成一个数字：

| 事件 | 含义 |
|---|---|
| `lease_reaped` reason=`lease_expired` | 租约到期被回收 |
| `lease_reaped` reason=`orphan_submitted` | 孤儿（本来就没有租约）被清扫 |

理由：**两者的处置与根因不同**。混成 `count` 会让运维以为「有租约过期了」，而孤儿根本没有租约。

## 六、触发时机：一个曾经不一致的地方

`reapExpiredLeases` 原来**只挂在 `dispatch` tick 上**：

- `mode: off` 时**没人回收**；
- 实测：重载后调 `task_next`，那 7 个孤儿毫无变化；改调 `dispatch` 才被清扫。

现在由**常驻协调器**接管（见 [05](05-协调器.md)），不再依赖 `dispatch` 是否在跑。
