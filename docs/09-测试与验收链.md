# 09 · 测试与验收链

> 怎么验证改动没弄坏东西，以及**为什么有些检查刻意不进验收链**。

## 一、一条命令

```bash
npm run verify      # 62 步
```

涵盖：契约、状态机、租约、证据、闸门、持久化、派发、协调器、容量、宿主服务、存储体检、e2e、泄漏闸门。

## 二、分层原则：只断言语义，不断言速度

| 类别 | 在验收链里 | 原因 |
|---|---|---|
| 语义正确性（契约、状态机、门禁） | ✅ | 有明确对错 |
| **性能探针**（`bench:*`） | ❌ | 时间断言进 CI，要么被噪声打红、要么被人调宽松到失去意义 |
| **规模演练**（`sim:cluster`） | ❌ | 同上 |
| **文档风格**（`tools/dev/audit-*.mjs`） | ❌ | 不是语义问题 |

**把时间断言放进 CI，两条路都会让这条链的公信力下降。**

### 一个现成的反面案例（就在验收链里）

`verify-journal-shared-cache.mjs` 曾断言「稳态轮 **< 3 ms**」。它要证明的其实是「**缓存生效了**」，却写成了「这台机器有多快」。

真实抖动：

```
rounds = 408.74 / 74.53 / 0.79 / 15.04 / 0.58 ms
第 4 轮抖到 15 ms → 判定失败，但功能完全正常
```

已改成**两条与机器快慢无关的判据**：

| 判据 | 表达什么 |
|---|---|
| 稳态中位数 **< 首轮 / 5** | 缓存确实起作用（不是每轮全量折叠） |
| 稳态最大值 **< 首轮** | 没有「偶尔走缓存、偶尔全量」的量级退化 |

改完实测 `153.02 / 22.22 / 0.44 / 0.31 / 0.32 ms`：稳态中位 0.32 ms 对首轮 153 ms（478×），连跑多次稳定通过。

**判据要盯「比例」和「方向」，不要盯「绝对毫秒」。** 前者跨机器成立，后者只在这台机器上成立。

## 三、泄漏闸门：查两处

`tests/verify-no-temp-leak.mjs` 是**验收链的最后一步**，查两个地方：

| 检查 | 判据 |
|---|---|
| 工作区插件目录 | 目录项必须在白名单里（`src`/`lib`/`tests`/`docs`/…） |
| **系统临时目录** | 本项目独有的前缀（`l0-jcache-` 等）必须为 0 项 |

### 为什么需要这道闸门

这个仓库在泄漏上栽过**五次**：

| 轮次 | 量 | 根因 |
|---|---|---|
| 第 25/26 轮 | 690 / 79 个 | 测试用相对 `stateDir` |
| 第 30 轮 | 换形态 | — |
| 第 40 轮 | **611 个 / 605 MB** | `stateDir: path.basename(...)` → 被 workspaceRoot 重解释 |
| 第 40 轮 | **1782 项 / 1.63 GB** | `mkdtempSync(os.tmpdir())` **零清理**，且闸门只查工作区 |
| 第 40 轮末 | 31 项 | **有清理但用了 `fs.rmSync`**（该环境静默失败）+ 闸门前缀漏了 `l0-recovery-drill-` |

**共同点不是「谁写错了」，而是：只提供正确写法、没有机制强制使用，而泄漏目录被 gitignore 挡住、`git status` 永远干净。**

### 闸门的前缀是「族」不是「枚举」

失败过两次的事实说明枚举式白名单不可靠：

| 版本 | 前缀 | 漏了什么 |
|---|---|---|
| 第一版 | `l0-jcache-` / `l0-jr-` / `^\.l0-probe-` / `n4-*` | `l0-recovery-drill-*`（29 个）、`l0-bounded-*`（因为不带点） |
| 第二版 | `^\.?l0-` | `n5-*`（e2e 全套用 `n5-chain` / `n5-oracle` / `n5-ts` / `n5-native` / `n5-g5`） |
| **现在** | `^\.?l0-` / `^l0control-` / **`^n\d-`** / `^dshhome-` | — |

所以改成**按族匹配**：`n\d-` 覆盖 n4/n5/n6…，`\.?l0-` 覆盖带不带点。**枚举式白名单在这个仓库已经漏过两次，不该有第三次。**

### 另一条：有清理 ≠ 清理成功了

`verify-partition-recovery-drill.mjs` 与 `verify-dispatch-view-bounded.mjs` 都**写了清理**，但用的是：

```js
fs.rmSync(dir, { recursive: true, force: true });   // 返回成功、不抛错、目录仍在
```

在那个环境里这个调用**会静默失败**（详见 `_temp-state.mjs` 顶部注释：工作区路径特有；tmpdir 下反而能删）。

现在统一改成 `removeTempDir()`（走 `removeTree`：逐个删文件再删目录，每步失败都记，能删多少算多少）。

> **删不掉的清理比没有清理更危险**，因为它让人以为已经处理了。

### 闸门自己也要被检验

每条闸门都验过**双向**：

- 正常情况：PASS
- **故意造一个残留**：必须红（`l0-jcache-FAKETEST` / `l0-recovery-drill-FAKE` / `n5-chain-FAKE` → 全部 `AssertionError`）
- 清掉之后：恢复 PASS

**一条永远不会红的闸门等于没有闸门。** 同理，一条永远在误报的规则也等于没有——比如文档审计里的「绝对用户目录」规则曾把 `C:\Users\<你>\.dsh` 这种**占位符**也报了，加了 `PLACEHOLDER` 过滤后才行。

## 四、测试写状态的硬要求

**`stateDir` 必须传绝对路径。**

service 会拿相对路径按 `workspaceRoot` 重新解释，于是状态落进源码目录、而清理钩子删的是另一个路径。

两个工具入口：

| 函数 | 建在哪 | 用在哪 |
|---|---|---|
| `tempStateDir(tag)` | **工作区内**（保持 workspaceRoot 与 stateDir 的相对关系） | 需要真实路径语义的测试 |
| `tempSystemDir(prefix)` | **系统临时目录**（自动登记 + 进程退出兜底删） | 不关心相对关系的测试 |

两者都走 `_temp-state.mjs`，进程退出时兜底清理。

> 那个文件里的 `removeTree` **不用 `fs.rmSync`**：实测该环境里 `rmSync(dir, {recursive:true})` 返回成功、不抛错、目录**仍然存在**。依赖它写清理 = 「看起来删了、其实没删」，而清理代码本身不会报错。

## 五、构建与类型

```bash
node scripts/build.mjs           # src/**.ts → lib/**.js
node scripts/build.mjs --check   # 校验 lib 与 src 同步（CI 用，不同步退出 1）
node scripts/typecheck.mjs       # tsc --noEmit（0 error 才算过）
```

**`lib/` 是入库的**（`main: lib/index.js`），所以改了 `src/` 必须重新构建——`build --check` 就是守这条的。

`typecheck` 用独立一步，是因为 `build.mjs` 用 Node 内置 `module.stripTypeScriptTypes()`：**只剥类型、不做类型检查**。依赖缺失时该步**判失败而不是跳过**。

## 六、e2e 与真 Agent

| 层次 | 用什么 | 覆盖什么 |
|---|---|---|
| 单元/契约 | `tests/verify-*.mjs` | 状态机、门禁、闸门、持久化 |
| e2e | `tests/e2e/*.mjs` | 跨层：图 → 派发 → 证据 → 审计 |
| **真 Agent** | 手动派真 session | **模拟 worker 绕开的路径** |

### 为什么真 Agent 必须单独跑

第 40 轮两个 P0 都是**只有真派 Agent 才暴露**的：

- 审计身份被解析成 producer（模拟 worker 用的是 fixture 里的实例名，不会撞）
- `submitted` + 租约过期 = 永久死锁（模拟 worker 提交后会立刻 verify，租约还没过期）

**模拟测试的盲区不是"覆盖不够"，而是"它走的路本来就不一样"。**
