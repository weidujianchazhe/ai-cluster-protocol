# 05 · 协调器

> 谁在自动回收卡住的节点、谁在派审计——以及为什么它**不派活**。

## 一、它解决什么问题（三条都来自实测）

### 1. `reap` 挂错了地方

只有 `dispatch` tick 会回收过期租约与孤儿。`mode: off` 时**没人做**。

实测：重载后调 `task_next`，那 7 个孤儿毫无变化；改调 `dispatch` 才被清扫。

### 2. 审计路由不可扩展

8 个 worker 就产生 8 条需要 Lead 手工转发的审计请求。**1000 个时不可能靠人做。**

### 3. worker 提交后不再心跳

租约到期后没人接手 → 节点卡住（详见 [03](03-租约与防重放.md)）。

## 二、它做什么

```
常驻 tick（默认 30s，unref 不阻止进程退出）
  ├─ reap：过期租约 + 孤儿 submitted
  └─ 审计路由：submitted 超时无人验 → 自动派审计实例
```

**它不派活。** 派活是 `dispatch` 的职责——两套调度逻辑必然漂移。

## 三、五条设计约束（决定了它为什么是「稳定」而不是又一个 hack）

| 约束 | 含义 |
|---|---|
| **确定性** | 纯状态机规则，**不含 LLM 判断**，可复现、可断言 |
| **幂等** | 每轮重算应有状态、做差集，不依赖上一轮的记忆 |
| **不越权** | 没有 Lead caller 时**只 reap、不派审计**（记 `no-lead-caller`）——不猜、不降级成别的身份乱派 |
| **可观测** | 每轮写 `coordinator_tick`，出问题能查「那一轮为什么没动作」 |
| **可关** | `coordinatorEnabled: false` 完全不启动；`auditDispatchAfterMs: 0` 只关自动审计 |

## 四、为什么它不是另一个 LLM agent

那会引入不确定性和成本：一个要思考的协调者，本身也是 LLM，也会卡住、也会烧 token。

这里全部是状态机规则——**能写成规则的，不要写成判断**。

## 五、审计路由的细节

```
遍历节点 → 找 status === 'submitted'
  → updated_at 超过 auditDispatchAfterMs（默认 120 s）
  → 且有 Lead caller
  → 派审计实例（职务 auditRole，默认 AUDIT_CODE）
```

### 防重复派：窗口必须与触发条件解耦

第一版把两者都用 `afterMs`，结果**配置 1 秒就等于每秒给同一节点派一个新审计实例**。

现在冷却窗是 `max(afterMs, 60s)`，与触发条件分开。

### 触发条件在真实环境下的表现

`submitted` 的节点如果在 120 s 内就完成了审计，就不会被接管——**这是对的**，自动路由只是兜底，不是主路径。

## 六、三个实现上的坑

### 1. `Number(0) || 120000` 会吃掉「0 = 关闭」

```ts
// 错的：
const afterMs = Math.max(5000, Number(cfg.auditDispatchAfterMs) || 120_000);
// 配置 0 → Number(0) = 0 是 falsy → 变成 120000 → 「关闭」反而等于「两分钟后派」
```

falsy 覆盖是配置项最常见的坑。现在显式判 `Number.isFinite`。

### 2. `reapExpiredLeases` 必须走 `withCore`

它内部用 `coreStore()`（AsyncLocalStorage）。直接把 `CorePersistence` 对象传进去，会因 `typeof !== 'function'` **静默返回空数组**——表现成「tick 跑了但什么都没回收」，**这是最难查的一类失败**。

### 3. 重入保护

上一轮没跑完（比如目录扫描很慢）时，新一轮直接跳过（`busy`），不让定时器叠加执行。否则慢盘上会堆起一层层未完成的 tick。

## 七、什么时候它会显得「没反应」

| 现象 | 原因 |
|---|---|
| 不派审计 | 没有 Lead caller（`no-lead-caller`）、或节点未超时、或冷却窗内（`recently-dispatched`） |
| 不回收 | 租约还活着（**活租约一律不碰**，这是对的） |
| 完全不启动 | `coordinatorEnabled: false`，或从未调用过任何工具（启动钩子在工具入口） |

## 八、手动调用

`coordinatorTick(reason, caller?)` 可以手动调，用于测试和运维。它和定时器走同一条路径，不会绕过任何规则。
