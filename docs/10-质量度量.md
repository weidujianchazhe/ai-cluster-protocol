# 10 · 质量度量

> 先能度量，才知道后面做的事有没有用。

## 一、它回答什么、不回答什么

| 回答 | 不回答 |
|---|---|
| 这批活**过程上**干得怎么样 | **产出本身好不好** |
| 证据是否可机器核验、有没有被独立审计、返工几次 | 一个 `verified` 的产物是不是平庸 |
| 哪些节点需要关注 | 该不该打回重做（它**不参与任何判定**） |

这个边界必须写在输出里（`measured` / `notMeasured` 两个字段），否则会被人当成「产出好坏评分」来用。

## 二、为什么是「聚合已有信号」而不是「新增评分字段」

节点完成条件是 `verify_done`——它验的是**有没有做完**，不是**做得好不好**。但「好不好」的原材料其实早在 journal 里了：

| 已有信号 | 原本用途 | 作为质量信号的含义 |
|---|---|---|
| `node.attempts` | 重试计数 | 返工多 = 过程质量低 |
| `evidence.provenance` | 只有 `verified` 能推 done | 来源强度 |
| `evidence.verdict` | 提交结论 | 审计判定 |
| `evidence.auditor_instance` | 独立性检查 | 有没有被独立审过 |

**所以第一步不需要改协议**。加字段是第二步（因果标注）的事。

## 三、四条设计约束（决定了它是「纯增量」）

| 约束 | 怎么保证 |
|---|---|
| **只读** | 不写 journal、不改状态；分数不落盘，随时可重算 |
| **可回放** | 同样的历史算出同样的分；不依赖当前时刻或外部状态 |
| **不参与判定** | `verify_done` / `pass_gate` / 派发闸门**都不看它** |
| **缺失就说缺失** | 无证据 → `unknown`（`score=null`），**不是 0 分** |

第三条尤其重要：**一旦质量分能挡活，它就从「观察」变成「判定」**，那会同时破坏可复现性与审计独立。

第四条是最容易做错的：**0 分会被读成「做得很差」，而 `unknown` 才是「还没法判断」**。混同会让人把「还没开始」当成「干砸了」，进而对没证据的节点做错误处置。

## 四、分数怎么算

四个维度加权：

| 维度 | 取值 | 权重 |
|---|---|---|
| `evidence` 证据来源强度 | `verified`=1 / `inferred`=0.5 / `assumed`=0.2 | 0.35 |
| `rework` 返工 | `1/(1+attempts)`：0 次=1，1 次=0.5，2 次=0.33 | 0.25 |
| `audit` 审计结论 | 有独立审计且 pass=1；无独立审计=**0** | 0.25 |
| `independence` 独立性 | 有独立审计=1，否则 0 | 0.15 |

总分 0–100，分档：`excellent` ≥85 / `good` ≥70 / `fair` ≥50 / `poor` <50 / `unknown`。

**每个节点都带 `reasons`**（可解释，不是黑箱），例如：

```
证据来源最强为 verified（1 条证据，1 条 pass）
返工 2 次 → 返工维度 0.333
有 1 个独立审计实例参与
```

## 五、实际输出

```
测什么  : 过程质量：证据是否可机器核验（verified）、是否被独立审计过、返工了几次
不测什么: 产出本身的好坏——一个 verified 的证据完全可能对应平庸的产物

总计    : {"nodes":4,"scored":3,"unknown":1,"avgScore":81,"grade":"good"}

按阶段聚合:
  audit      scored= 1 unknown=0 avg= 60 fair
  build      scored= 1 unknown=0 avg= 83 good
  deliver    scored= 0 unknown=1 avg=  — unknown    ← 无证据，不混进均值
  research   scored= 1 unknown=0 avg=100 excellent

最需关注（升序）:
  AUDIT     score= 60 fair       | 证据来源最强为 verified（1 条证据，1 条 pass）
  BUILD     score= 83 good       | …返工 2 次
  RESEARCH  score=100 excellent  | …
```

## 六、三个刻意的设计选择

### ① `unknown` 单独计数，不混进均值

`byStage.deliver` 的 `scored=0 / unknown=1 / avg=—`：那一个节点没证据，它**不影响**均值。若把它当 0 分算，`deliver` 阶段的均值会变成 0，看起来像「交付做得很差」，实际上只是还没开始。

### ② `attention` 只列有分数的

「最需关注的 5 个」按分数升序。**没有分数的节点不进这个列表**——否则「还没做」会挤掉「做砸了」的位置。

### ③ 分组用 `avgScore` + `distribution` 两个视角

只看均值会被极值骗（1 个 100 分 + 3 个 50 分，均值和 4 个 62.5 分一样）。`distribution` 给出各档数量，能看出是「普遍中等」还是「两极分化」。

## 七、怎么用

```text
quality_report()                        # 全图
quality_report({ stage: "build" })      # 只看某阶段
quality_report({ limit: 200 })          # 多要些明细
```

**权限**：`quality.read` 给全部 9 个角色。理由是纯只读聚合——把它锁起来只会让人「不知道这批活干得怎么样」。

## 九、返工分因（用真实数据发现的修正）

### 问题

`attempts` 把两种完全不同的东西混在一起：

| 情况 | 该不该扣质量分 |
|---|---|
| worker 产出不合格被打回 | **该扣** |
| 租约过期 / 孤儿清扫，被迫重新 claim | **不该扣**（那是状态机坑了它） |

**真实数据里就看到这个后果**：`M8-01..08` 八个节点全被判 `poor (43)`，但那 2 次返工是**租约死锁**逼出来的，产出本身没问题。质量分把「系统故障受害者」记成了「干得差的 worker」。

### 真实 journal 里的原因分布

```
attempts_changed 原因：
  lease_expired                    14  ← 系统
  rejected:orphan_submitted         7  ← 系统（就是那 8 个 M8 节点）
  rejected:credential_unavailable   4  ← 业务
```

### 修法：白名单式系统原因

```ts
SYSTEM_REWORK_REASONS = ['lease_expired', 'orphan_submitted', 'lease_takeover', 'lease_reaped']
```

**只把明确列出的算系统原因，其余全算业务。**

为什么是白名单而不是黑名单：

> 宁可把系统原因误判成业务（多扣分），也不能把业务失败洗成系统原因（免罚）。
> **虚高的质量分比虚低的更危险**——它会让人以为没问题。

### 输出新增两个字段

```json
"sample": {
  "attempts": 2,
  "businessRework": 0,
  "systemRetries": 2
}
```

质量分**只用 `businessRework`**；`systemRetries` 仅展示，并在 `reasons` 里说明。

### 重算结果（真实数据）

| 节点 | 修复前 | 修复后 | 业务 | 系统 |
|---|---|---|---|---|
| M8-01 ~ M8-08 | **43 / poor** | **60 / fair** | 0 | 2 |
| MB-PROV-01 | 43 / poor | **43 / poor** | 2 | 0 |
| FOCUS | 48 / poor | 48 / poor | 1 | 0 |
| RET | 48 / poor | 48 / poor | 1 | 0 |

**8/8 个 M8 节点分数提升**，其余不变——说明分因正确：该扣的没洗白，不该扣的没冤枉。

### 一个连带的性能修正

`buildReworkIndex(store)` **一次扫 journal** 建索引，供所有节点复用。不这么做的话每个节点各扫一遍 → O(节点数 × 事件数)。`qualityReport` 与 `collaborationMap` 都传同一个索引。

## 十、踩了三次的坑：camelCase vs snake_case

| 位置 | 字段名 |
|---|---|
| 内存里的 `EventRecord` | `node_id`（snake_case） |
| 落盘的 `journal.jsonl` | `nodeId`（**camelCase**） |
| 落盘的 `snapshot.json` | `nodeId`（**camelCase**），且 **evidence 被裁剪**（缺 `provenance` / `producer` / `auditor`） |

这个不一致在一天之内让人踩了三次：

1. 读 snapshot 做分析 → 全是 `undefined`
2. 读 journal 折 evidence → 字段名对不上
3. `buildReworkIndex` 扫 journal → `ev.node_id` 是 undefined，**索引静默为空**

**修法**：`buildReworkIndex` 同时认 `node_id` 和 `nodeId`。

**教训**：**静默为空比抛错更危险**——索引看起来"正常但为空"，于是所有节点都走了"全算业务"的退化路径，而这个退化路径**不报错**。类似的坑在这个项目里已经出现过多次（`fs.rmSync` 静默失败、`Number(0) || 120000` 吃掉 0 语义）。
