# 07 · 数据落点与持久化

> **开工前读这一篇。** 跑起来之后才发现盘满了，迁移成本远高于现在改一个环境变量。

## 一、三处落点

| 数据 | 落在哪 | 增长速率 | 可控 |
|---|---|---|---|
| **协作记录**（journal / 快照 / 证据） | **工作区下 `.l0-control/`** | journal 约 **4.2 KB/节点**；分段上限 512 MB（≈50 万节点） | ✅ 跟随工作区，`stateDir` 可配 |
| **每个 Agent 的会话** | **`$DSH_HOME/sessions/`** | **约 1–1.3 MB/会话** | ⚠️ **默认就在系统盘** |
| 测试/自检临时目录 | `os.tmpdir()` | 量小 | 可用 `TEMP` 改 |

### 为什么协作记录天生可控

```ts
this.stateDir = path.resolve(this.workspaceRoot, this.config.stateDir);
// stateDir 默认 '.l0-control'（相对）→ 工作区在数据盘，记录就在数据盘 ✅
```

`workspaceRoot` 默认取宿主的 `workingDirectory.defaultDirectory`，所以**工作区在哪，记录就在哪**。

## 二、真正会失控的是会话数据

会话按工作区分目录，只增不减。实测（一台跑了三个月的机器）：

| 工作区 | 会话数 | 体积 |
|---|---|---|
| 本项目 | 97 | 88.8 MB |
| 另一个项目 | 43 | 80.0 MB |
| 又一个 | 12 | 42.8 MB |
| 其余 | 35 | 30 MB |
| **合计** | **187** | **242 MB** |

⇒ **平均 1.29 MB/会话**（文件是 `session.v4.jsonl.zstd`，zstd 压缩的对话流）。

### 按规模算

| Agent 数 | 会话数据 |
|---|---|
| 100 | ≈ 0.13 GB |
| **1000** | **≈ 1.26 GB** |
| 10000 | ≈ 12.6 GB |

## 三、`env_check` 会提前告诉你

启用协作后**首次工具调用**自动跑一次（写 `storage_ok` / `storage_tight`，只写一次），也可以主动调 `env_check`：

```json
{
  "ready": true,
  "blockers": [],
  "storage": {
    "ok": false,
    "systemDrive": "C:",
    "drives": [{ "root": "C:", "freeGb": 13.7, "totalGb": 123.1 },
               { "root": "F:", "freeGb": 191.8, "totalGb": 465.3 }],
    "warnings": ["Agent 会话集中写在系统盘 C:（可用 13.7 GB）。实测 1.30 MB/会话 → 1000 个 Agent 约 1.27 GB…"],
    "advice": ["把 DSH 数据目录迁到更宽的盘（F: 现可用 191.8 GB）：setx DSH_HOME \"F:\\dsh-home\"…"]
  },
  "scale": { "perAgentMb": 1.3, "for1000AgentsGb": 1.27, "suggestedMaxAgents": 5395 }
}
```

**估算用实测速率**（数一遍已有会话算平均），不是拍一个常数。

### 告警阈值（刻意保守）

只在「会话在系统盘」且满足其一才喊：

- 可用 < **20 GB**，或
- 千级预估 > 可用空间的 **30%**

理由：对「小项目本来就在 C 盘」天天喊狼来了，就会被人关掉。

## 四、迁走会话数据

`DSH_HOME` 是**宿主环境变量**，插件不会偷偷改它（改了要重启，且影响所有 profile）：

```powershell
# Windows（用户级，重开 DSH 生效）
setx DSH_HOME "F:\dsh-home"
# 迁移前先把旧目录内容搬过去： C:\Users\<你>\.dsh  →  F:\dsh-home

# macOS / Linux
export DSH_HOME=/data/dsh-home
```

改了之后 `sessions` / `profiles` / `dsh-runtimes` **整体跟着走**。

**这是唯一能一次性根治的办法**——只做目录联接（junction）DSH 不保证认。

## 五、清理

| 目标 | 怎么做 | 注意 |
|---|---|---|
| 旧会话 | 删 `$DSH_HOME/sessions/<工作区>/` 下不需要的 | 删的是历史对话，**不影响工作图与证据** |
| journal 封存段 | `journal.0001.jsonl`… 可归档到别的盘 | **别删活动段** `journal.jsonl` |
| `node_modules` | 只在想改代码时需要 | 安装插件本身**零运行时依赖** |

## 六、持久化的分层

```
core journal（哈希链，权威）      ← 事件源，可回放
  ├─ snapshot.json（加速器）      ← 锚点不符就退回全量重放
  └─ journal.000N.jsonl（封存）   ← 活动段恒为 journal.jsonl
```

细节与「为什么活动段不能带段号」见 [01 状态与日志](01-状态与日志.md)。

## 七、一个同类坑：临时目录泄漏

本项目自己的测试曾经把垃圾倒在系统临时目录里：**1782 项 / 1.63 GB**（`l0-jcache-*` 546 个 + `l0-jr-*` 1234 个），根因是两个测试用了 `fs.mkdtempSync(os.tmpdir(), ...)` 却**零清理**。

现在：

- 测试用 `tempSystemDir()`（自动登记 + 进程退出兜底删）；
- **泄漏闸门查两处**：工作区插件目录 **和** 系统临时目录。

**泄漏在哪都算泄漏，闸门就必须看到哪。**
