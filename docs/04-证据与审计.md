# 04 · 证据与审计

> 什么算「完成」、为什么审计不能是自己、以及一条「合法审计必然失败」的路径。

## 一、证据必须对应真实产物

`acceptance` 由插件**对磁盘上的文件机器判定**：

| kind | 判定 |
|---|---|
| `exists` | 文件存在 |
| `sha256` | 内容哈希匹配 |
| `contains` | 包含指定字符串 |

**判定不了就是 `unknown`，绝不当 pass。** `unknown` 不得通过任何闸门——这是 fail-closed 的核心一条。

## 二、来源分级：只有 `verified` 能支撑完成

| 级别 | 什么时候是它 | 能推开 `done` 吗 |
|---|---|---|
| `verified` | 显式传了 `acceptance` 且机器判定命中 | ✅ |
| `inferred` | 只有人写的结论，没有机器判定 | ❌ |
| `assumed` | 明确标注为假设 | ❌ |

缺省规则：**有 `acceptance` → `verified`；没有 → `inferred`。** 显式给值永远优先，非法值直接拒（`invalid-provenance`）。

这条防止的是最常见的一种虚报：**「我写了一句『已测试通过』」被当成「测试通过」**。

## 三、审计独立性是结构性的，不是提醒

| 要求 | 说明 |
|---|---|
| `producer_instance ≠ auditor_instance` | 生产方不能自己审自己 |
| 审计方职务必须在白名单 | `[AUDIT, AUDIT_CODE, AUDIT_EVIDENCE, AUDIT_DESIGN]` |
| 结论未知不得通过 | `unknown` 一律拒 |

三件事在代码里是**硬门禁**，不是文档里的一句话。

## 四、一条「合法审计必然失败」的路径

这是本节最值得记的一段。

### 现象

```
ok=false  error=forbidden (403, action=verify_done, actor.id=role-code-62)
```

`role-code-62` 正是该节点的**生产者**。所以看起来像「自审被拒」——很合理。**但它其实是身份认错了。**

### 链路

```
契约建议审计方省略 auditor_instance（服务会用自己的实例名）
  → resolveActor 候选: instanceId → auditor_instance → **producer_instance** → 活 Agent
  → 省略后落到 producer_instance
  → actor 被认成生产者
  → 职务 CODE 不在 verify_done 白名单
  → 403，报的却是"自审"
```

**按契约做事的合法审计，必然失败。**

### 为什么不能简单删掉那个候选

因为 `evidence.add` 的白名单是 `[RESEARCH, DESIGN, CODE, DELIVER, PLUGIN]`——**不含 ORCH/HUMAN**，而生产 worker 正是靠 `producer_instance` 拿到 CODE 职务的。

**无条件删会让证据提交全断。**

### 修法

**只对审计动作排除**：

1. `resolveActor` 增加 `excludeProducer`；
2. `index.ts` 对 `verify_done` 先试 `callerInstance(exec.agent)` 解析成**实例名**（职务正确、日志可读），失败才退回排除 producer 的版本。

### 修完的效果

| 时点 | 错误 |
|---|---|
| 修复前 | `forbidden (actor.id=role-code-62)` ← 认成生产者 |
| 修复后 | **`auditor-required`** ← 不再是生产者，而是「这个会话没绑定实例」 |

**这是正确的错误**：报的是真实原因，而不是「你在自审」。

## 五、一个未完全对齐的疑点（如实记）

`M8-02` / `M8-04` / `M8-08` 当时**成功了**，而 `M8-03` 被 403。

若根因是「producer 覆盖 actor」，前者也该失败。最可能的解释是那几次审计**显式传了 `auditor_instance`**——但 worker 的回报里没写，**无法确认**。

记在这里而不是抹掉：**一个解释了大部分现象但解释不了全部的理论，比没有任何理论更危险**，因为它会让人停止继续查。

## 六、阶段闸门（`pass_gate`）

五段，可分别通过：

```
research → design → build → audit → deliver
```

`verify_done` 要求对应阶段的闸门已 passed。所以顺序是：**先 `pass_gate` 再 `verify_done`**，否则会收到「阶段闸门未通过：build」。

## 七、决策记录（`decision_record`）

L0–L2 的决策走 `decision_record` 落账；**L3 不经此工具**（那属于更上层）。记的是「选了哪个选项、为什么」，供事后追溯。
