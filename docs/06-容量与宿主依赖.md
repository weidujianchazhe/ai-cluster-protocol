# 06 · 容量与宿主依赖

> 「能跑多大」被三层限制卡住，其中**两层不归本插件管**。

## 一、三层限制

```
① maxParallel              本插件：同时活的租约数（默认 64）
② teamMemberLimit          宿主 agentTeams.maxMembers（默认 16 → 插件自动抬到 256）
③ subagentMaxActive        宿主 subagents.maxActiveSubagents（默认 8 → 插件自动抬到 256）
```

**只调 ① 是没用的**：宿主默认只允许 8 个子会话同时活，第 9 个起报：

```
subagent limit reached (active child limit: 8)
failureCode: "host-capacity"  retryable: true  retryAfterMs: null
```

（这条就是早期「32 并发只到 8」的原因。）

### 抬到 256 之后实测：32/32 同时活

这不是"配置写上了"，是真跑过。探针在 `artifacts/calib/conc32`：每个子会话自己写下 `start-<N>.json` 与 `end-<N>.json` 两个时间戳，中间 `Start-Sleep 75` 持锁；32 个时间戳区间做打点，求同时活着的峰值。

| 项 | 实测 |
|---|---|
| 发起的并发 spawn | 32 |
| **同时活着的会话（区间打点求峰）** | **32** |
| 完成数 | **32 / 32** |
| 持锁时长中位数 | 78.6 s（75 s sleep + 进程启动开销） |
| `active child limit` 报错 | **0 次** |
| journal 里 `agent_spawned` 条数 | 32（一条不少） |

**它证明了什么**：宿主接受 32 个子会话同时活着；「32 并发只剩 8」的那个天花板确实来自 `subagents.maxActiveSubagents=8`，不来自本插件。

**它没证明什么**：32 ≠ 256 ≠ 1000；而且这 32 个会话持锁期间是**阻塞在一次工具调用上**，不是各自跑满 LLM 推理——并发"槽位"能占满，不等于 token 吞吐跟得上。

### 再往上压：54 个会话把宿主打崩了

同一套探针加档到 64（分两批 32）时，宿主倒了。这不是推测，有崩溃日志。

```
20:30:57 – 20:31:43   54 个子会话在 46 秒内进入持锁（写了 start-*.json）
20:31:45              宿主进程以 code 1 退出
20:33:14              Electron 壳把 host 拉起来（GUI 端口 5327 → 4373）
结果                  start=54, end=0 —— 54 个会话全部在持锁中途消失
```

崩溃日志 `%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-2026-11-22T12-31-45-484Z-host.log`：

```
dsh: fatal uncaught exception: Error: inspector: source state exceeds the source-frame byte limit
    at InspectorSourceBuffer.setState (.../@deepseek-ai/dsh-experimental-inspector/lib/index.js:996:10)
    at HostBridgePublisher.setState (...:1109:16)
    at HostInspectorSource.setState (...:836:18)
    at publish (...:2294:3)
```

**三条结论，每条都要么纠正了猜测、要么被日志钉死：**

1. **崩点在宿主的 `dsh-experimental-inspector`**，不在本插件——堆栈里没有一行 `dsh-l0-control`。它要给每个会话/每次工具调用发布 inspection source，并发一多，累计帧超过自己的字节上限就抛未捕获异常，整个 host 退出。
2. **不是内存 OOM**。崩的时候物理内存还剩 3–4 GB、提交 12–18 GB（上限 51.8 GB）。之前"256 要 19 GB 装不下"的推算被推翻了——**内存还没到极限，先崩的是 inspector**。
3. **触发条件确实是并发**：32 稳、54 崩，中间没有别的变量。

旁证（不是原因，但同期出现）：20:29–20:34 系统日志密集出现 `WHEA-Logger 17 已更正的硬件错误`——内存/缓存的纠错告警，说明这台机器在密集分配时硬件层面也在吃力。

**所以「千级」的当前答案**：不是本插件撑不住，是**宿主侧的 inspector 在 50 附近先崩**。要到 256 必须先摘掉这条路径（禁用 `dsh-experimental-inspector` 后复测 64/128），否则任何并发标定都会在同一处复现。

## 二、②③ 的关键差异：一个活引用，一个构造时快照

这一点必须逐个读源码确认，**不能类推**：

| 配置 | 何时读取 | 改完要重启吗 |
|---|---|---|
| `subagents.maxActiveSubagents` | **每次开子会话现读**（`() => config.maxActiveSubagents.get()`） | ❌ 立即生效 |
| `agentTeams.maxMembers` | **构造时传给 roster** | 需重载插件 |

源码依据（`@deepseek-ai/dsh-subagent`）：

```js
static Config = z.object({
  maxDepth:           z.number().default(1).volatile(),
  maxActiveSubagents: z.number().default(8).volatile(),   // ← 默认 8，schema 上限 MAX_SAFE_INTEGER
})
const releaseSlot = pool.reserve(this.maxActiveSubagents())   // 每次现读
```

**两个结论**：

1. 它是 **Cordis 配置项**，默认 8，不是硬编码——**可以调**；
2. 它是**活引用**，改完立即生效。

## 三、插件怎么处理这两层

启用协作时自动 raise，并把结果写进 journal：

| 事件 | 含义 |
|---|---|
| `team_limit_raised` / `subagent_capacity_raised` | 抬成功了（带 from / to） |
| `team_limit_kept` / `subagent_capacity_kept` | 本来就更大，没动 |
| `team_limit_unavailable` / `subagent_capacity_unavailable` | 那个服务不存在 |
| `*_failed` | 赋值了但**回读确认没生效**（只读 ref、被包一层等） |

**回读确认**是必须的：不假设赋值成功。失败不阻断启用，但绝不谎报成功。

## 四、宿主服务依赖（缺了会怎样）

本插件的 `inject` 只有 `['tools']`，其余全是运行时 `ctx.get()`。**缺了不会报错，只会静默降级**——所以首次工具调用会自检一次（`host_services_ok` / `host_service_missing`，只写一次）。

| 服务 | 谁提供 | 缺了会怎样 |
|---|---|---|
| `subagents` | DSH 内置 | **完全派不出子会话** |
| `sessionController` | DSH 内置 | 无法续跑既有会话、无法转发消息 |
| `agentTeams` | **`@deepseek-ai/dsh-experimental-agent-team`（DSH 自带，需在 profile 启用）** | `agent_spawn` 全退回 activation（子实例**不能**当 TeamTask owner）；`teamMemberLimit` 放开无效；**其余功能正常** |

`graph_status.capabilities.hostServices` 直接暴露这个视图，不用翻 journal。

## 五、Agent 预设：默认继承，不假设别人装了什么

`defaultAgentPreset` **默认空串 = 子实例继承父会话的预设**。

**不要**把它设成某个具体名字（比如 `memory-first`）除非你确认那个包装了——宿主对「指定了但没注册的预设」是**直接抛错**：

```js
if (composition.agentPreset !== undefined) {
  const presets = childCtx.get('agentPresets');
  if (presets === undefined) throw new SubagentError('...', 'PRESET_UNAVAILABLE');
  return presets.mount(childCtx, composition.agentPreset);   // 未知名字在这里失败
}
```

**不是降级，是派不出去。**

而不传时宿主走 `selectedPreset ?? parent.composedPreset(parent)` —— 子实例继承父的预设，既不需要那个包存在，也不丢父会话的能力。

> 历史上这里硬编码过 `'memory-first'`。本机装了（`presets/memory-first` 通过 Junction 进 profile），所以没暴露；**别人没装就会在第一次派发时失败**。

## 六、同一个形态出现了三次

| # | 隐患 | 后果 | 为什么没早发现 |
|---|---|---|---|
| 1 | 缺 `agentTeams` 服务 | 静默降级（能力丢失） | 只在返回值 `via` / `ownerCapable` 里体现 |
| 2 | 测试泄漏到系统临时目录 | 累积 **1.63 GB** | 泄漏闸门只查工作区，没查 tmpdir |
| 3 | 硬编码 `memory-first` 预设 | **spawn 直接失败** | 本机装了 |

**共同形态**：本机装了某个东西所以能跑，别人没装就在**运行期**失败，且**不在安装期报错**。

所以现在的原则：**不假设任何外部东西存在；缺了要么自愈（继承），要么显式告警（自检），绝不静默降级。**

## 七、向后推算「能跑多少」

`env_check` 的 `suggestedMaxAgents` 按会话盘可用空间反推（保守：只用一半）。

它只算**会话数据**（约 1.3 MB/个），不含 journal（journal 在工作区，跟随 `stateDir`）。详见 [07](07-数据落点与持久化.md)。
