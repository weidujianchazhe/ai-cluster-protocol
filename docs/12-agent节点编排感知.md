# 12 · agent 节点编排感知

> ③ 的那一步：分区本来只用来**限流**，现在接上**感知**。
>
> 名字从「邻域感知」改成「agent 节点编排感知」——它不只是"同分区里看看邻居"，
> 而是**编排层能看见什么**的完整定义：纵向看上游、横向看同域、全景看耦合与质量。
>
> 文档 A1 留了一个**关于"能不能内化成模型内部 MoE 专家编排"的猜想**，附技术边界与
> 一条经济学判断：**它优化的是"能干多大的工程"，不是"多快多省"**。

## 一、感知什么

同分区内**已完成**节点的定长摘要：

```json
{
  "partitionId": "p1",
  "neighbors": [
    { "nodeId": "ARCH", "title": "架构与接口", "summary": "定义了三类接口…", "doneAt": "…", "verifiedEvidence": 1 }
  ],
  "totals": { "inPartition": 5, "done": 2, "shown": 2 },
  "cost": { "approxTokens": 103, "chars": 310 }
}
```

## 二、三条硬约束（缺一条就会破坏已有性质）

### ① 单向

新节点读已完成的邻居；邻居**不知道**自己被读，也不参与任何等待。所以执行顺序不变，不会出现「互相等对方」。

### ② 无环 —— 只读 `done`

这是关键。`done` 是**终态、不可退出**，所以"某时刻有哪些 done 邻居"由 journal 的 seq 唯一决定：

```
同一段历史 → 回放出同一个邻域 → 可复现
```

**如果允许读进行中的节点**，邻域会随时刻漂移——那才是破坏可复现。所以「只读 done」不只是保守，是可复现的必要条件。

### ③ 只读 `title` / `spec`，不读盘

读盘会让「感知」变成 I/O 依赖，成本不可控，也会让 worker 陷入「读到别人的半成品」。

## 三、成本必须算清楚

「让节点知道更多」在这套架构里是按 **`maxParallel × 每轮上下文`** 线性放大的。所以：

| 做法 | 说明 |
|---|---|
| **定长截断** | `maxNeighbors`（默认 5）/ `charsPerNeighbor`（默认 120）⇒ 约 600–800 token/节点，**不随图规模增长** |
| **成本随返回** | `cost.approxTokens` 让调用方知道自己买了多少 |
| **按需调用** | 它是独立工具，不调用就不花。**零默认成本** |

按默认值算：1000 个节点 ≈ 60–80 万 token 额外消耗。**这个数字必须写在输出里**，否则「让节点知道更多」就是不算账。

## 四、它会破坏可复现吗

**不会，但它也不提供"产出可复现"。**

整套系统的可复现承诺只到**决策层**（就绪计算、派发闸门、租约），不到**产出自生成**——worker 是 LLM，本身有随机性。

所以邻域摘要**不降低**任何现有承诺：它只是给 worker 多了一段**确定性生成的输入**。

## 五、四个刻意的设计选择

### ① 不含自己

`nodeId === 自己` 的节点被跳过。含自己会让 worker 读到自己刚写了一半的 spec，纯噪音。

### ② 排序稳定

按 `doneAt` 降序（最近的在前），时间相同按 `nodeId` 排。**两次调用必须同顺序**——排序不稳定就谈不上可复现。

### ③ 截断时明确说明

```json
"caveat": "还有 3 个已完成邻居未展示（受 maxNeighbors 限制）"
```

**静默少给会让人以为邻域就那么大。**

### ④ 不在分区里 → 优雅返回，不抛错

```json
{ "ok": true, "partitionId": null, "caveat": "no-partition",
  "note": "该节点不在任何分区里…要启用邻域感知，把它放进 coordination.partitions[].nodeRefs。" }
```

不在分区是**正常的**（大多数图根本没有分区），不是错误。

## 六、`verifiedEvidence` 是个提示，不是判定

每条摘要带 `verifiedEvidence`（该邻居有几条 verified 证据）。它是个**粗糙的可信度线索**：

- 0 条 → 这活完成了但没有机器核验过的证据
- 多条 → 有交叉验证

**它不参与任何判定**，只是让读的人有个初步印象。

## 七、怎么用

```text
neighbor_digest({ nodeId: "BUILD" })                              # 默认 5 条 × 120 字
neighbor_digest({ nodeId: "BUILD", maxNeighbors: 3 })             # 更省
neighbor_digest({ nodeId: "BUILD", charsPerNeighbor: 60 })        # 更省
```

**权限**：`neighbor.read` 给全部 9 个角色。

## 八、这一层做完，① ② ③ 串起来是什么

```
① quality_report     →  单节点质量分
② collaboration_map  →  谁读了谁 + 有耦合/无耦合的质量差
③ neighbor_digest    →  当节点真要"参考邻居"时，把邻居摘要递给它
```

三者的关系是**从观察到行动的梯度**：

| 步骤 | 改变什么 | 成本 |
|---|---|---|
| ① | 让质量**可见** | 零（纯读 journal） |
| ② | 让耦合**可见** | 零（纯读 journal） |
| ③ | 让节点**能参考**邻居 | **约 600–800 token/节点**（按需） |

**只有 ③ 真正改变了 worker 能拿到的信息**。①② 是测量工具，③ 是行动工具。

## 九、还没做的（④ 及以后）

| 项 | 为什么先不做 |
|---|---|
| **产物引用校验** | 验证「B 真的用了 A 的成果」需要格式约定，成本不低；先把「声明图」跑起来看有没有用 |
| **跨分区感知** | 现在是同分区；跨区会让邻域大小不可控 |
| **读进行中节点** | 会破坏可复现（邻域随时刻漂移），除非引入快照语义 |
| **让邻居知道自己被读** | 那就变成双向通信，可复现与成本线性都会受威胁 |

## 十、纵向：只读直接上游（`direction: 'deps'`）

横向（同分区）之外，还有一维**更重要**的纵向：**直接依赖**。

### 为什么纵向比横向更该做

| 理由 | 说明 |
|---|---|
| **`deps` 是显式的** | 写在 graph 里，不需要有人去配 `partitions`。实际图里常常一个分区都没有，但每个节点都有 deps |
| **能 claim 时上游必然已完成** | `deps` 全 `done` 是节点变 `ready` 的前提 ⇒ 读纵向**一定有数据**，不会像横向那样常常返回空 |
| **比横向更严守可复现** | 横向取决于"分区里还有谁"，纵向只取决于**这个节点自己的 deps**（静态）+ `done`（终态）⇒ 完全确定 |

### 深度只到 1

`deps` 是 DAG，递归读祖先会爆：

```
节点 C 的 deps = [B1, B2]
B1 的 deps = [A1, A2, A3]
A1 的 deps = [R1, R2, R3, R4]
→ 深度 3 就有 4×3×2 = 24 个祖先
```

**深度 1 是安全的；更深的要看真需求再谈。**

### 三种方向

```text
direction: 'partition'   ← 横向（默认，保持旧行为）
           'deps'        ← 纵向深度 1（直接上游）
           'both'        ← 两向合并
```

### 合并时**上游优先**

名额有限时（`maxNeighbors`）先给上游。理由：

> 上游是「我依赖的东西」，不读它就做不对；同分区是「同域里别人做了什么」，略过几个不影响正确性。

同一个节点如果既在上游又在分区里，**只算一次**（保留 `dep` 标记）。

每条摘要带 `via: 'dep' | 'partition'`，让人知道这条是"我上游"还是"我同域"。

### 上游未完成时

`deps` 里没 done 的节点**不出现**，并给出机器标记与人读说明：

```json
"caveatFlags": ["deps-pending"],
"caveat": "3 个依赖里有 2 个尚未完成，未纳入邻域"
```

## 十一、`caveatFlags` 与 `caveat` 为什么要分开

这是实现中撞到的一个真实退化：

| 版本 | 形式 | 问题 |
|---|---|---|
| 第一版 | `caveat: 'no-partition'` | 程序可判，但**人读不懂** |
| 第二版 | `caveat: '该节点不在任何分区里…'` | 人能读，但**程序失去依据**（测试立刻红了） |

**两个消费者需要两种形式**，所以现在都给：

| 字段 | 给谁 | 内容 |
|---|---|---|
| `caveatFlags` | **程序** | `no-partition` / `deps-pending` / `truncated` |
| `caveat` | **人** | 上面每条的展开说明，用 `；` 连接 |

这不是冗余——**把机器判据和人类可读混成一个字段，总有一边会退化**。

## 十二、成本对照

| 方向 | 默认成本 | 特点 |
|---|---|---|
| `partition` | 5 条 × 120 字 ≈ 600–800 token | 常常为空（要先建分区） |
| `deps` | 同上 | **基本一定有数据**（能 claim 说明上游已 done） |
| `both` | 合并后仍受 `maxNeighbors` 限制 | 上游优先占用名额 |

**纵向是更划算的那一维**：同样成本，命中率高得多。

## 十三、组织位置的感知：我有没有和别人撞写域

上面十二节讲的都是「**内容**感知」——别人做出了什么。还有一类感知是「**位置**感知」——我在组织里站在哪、会不会跟人踩同一块地。它由另一个只读工具回答：

```json
organization_review → signals[]
  { "kind": "write-scope-overlap", "owner": "agent",
    "nodes": ["API", "UI"], "detail": "重叠写域：src/api/ ~ src/api/v2/ …" }
```

三个刻意的设计：

1. **worker 自己就能查**（`organization_review` 在 `BASE_TOOLS` 里）。撞写域这种问题上报给 Lead 再转述一圈，等回来时两边都已经写完并互相覆盖了。
2. **但改不了图**（`graph_replan` **故意不在** `BASE_TOOLS` 里）。查得到 ≠ 有权改：人人可单方面改图，等于没有协调。
3. **`writeScopes` 只是声明，不是文件锁**。重叠信号说的是「你们大概率会踩到同一处」，不是「系统已阻止」。真要有强制力得靠串行化或所有权划分，现在只做到「报出来 + 给草案」。

这一层是**发现**，不是裁决：`signals` 里有 `requiresGraphChange` 和 `owner`，但它们只是建议——采纳与否由调用方决定，且必须显式走 `graph_replan`（见 [14](14-组织因子与协调闭环设计.md)）。

## 十四、猜想：能不能内化成模型内部的 MoE 专家编排

> 这一节原本在这里展开，现已**独立成篇**：[**14 MoE 专家编排猜想**](A1-MoE专家编排猜想.md)。

一句话概括：

> 内化成 MoE 不是优化，是**换一个不同的问题**——而且它优化的不是性能，是
> 「**能干多大的工程**」；代价是**更多算力占用**与**更高的门槛**。

三条不能撞的墙：**没有梯度**（质量分不可微）、**没有共享表示**（文本接口到不了 hidden state）、
**失败语义不同**（MoE 没有"专家算错了"，我们有 `rejected` 阻塞下游）。

五维对照表、"它到底优化了什么"的经济学判断、以及"各层能触及什么"，都在
[A1 MoE 专家编排猜想](A1-MoE专家编排猜想.md)。
