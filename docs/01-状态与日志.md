# 01 · 状态与日志

> 状态从哪里来、存在哪、怎么恢复、坏了怎么发现。

## 一、单一事实源

节点、依赖、租约、证据、阶段闸门、决策——全部由**事件日志折叠**得出，不做第二份状态。

```
事件 → fold → State{nodes, edges, leases, evidence, gates, decisions, cursors}
```

这决定的几件事：

- **可回放**：重启后从 journal 重建，不依赖任何快照的正确性。
- **可校验**：链断了立刻报，不给「看起来正常」的中间态。
- **不可静默截断**：少读一半历史会显式失败，而不是安静地少看。

## 二、哈希链

每条事件带 `seq` / `prevHash` / `hash`，逐条相接：

| 检查 | 失败码 | 含义 |
|---|---|---|
| `seq` 必须连续 | `STATE_SEQ_GAP` | 中间缺了事件 |
| `prevHash` 必须等于上一条的 `hash` | `STATE_HASH_BREAK` | 历史被改过或拼接错位 |

恢复时先验链，再折叠。链本身坏了就不往下走——**折叠一份不可信的历史没有意义**。

## 三、两本账

| 账本 | 内容 | 用途 | 参与状态推导 |
|---|---|---|---|
| **core journal（哈希链）** | 节点/租约/证据/闸门/决策 | 权威状态源 | ✅ |
| **扁平日志（N3）** | 派发登记、tick、闸门归因、访问审计 | 「刚才为什么没派」 | ❌ |

两个账本各写各的，但**同一件事必须两边都落**。反例（真实踩过）：只回收租约不写派发登记，节点会「重新可就绪、却再也不会被派出去」——因为派发层看的是登记表，而那张表里它还挂着「已派出未领取」。

协调动作也守这条规则，但**拆成两半**：

| 记什么 | 落在哪 | 为什么不放一起 |
|---|---|---|
| `graph_replanned`（增删了哪些节点、`rewired` 新旧依赖、`graph_version`） | core journal（哈希链） | 它改变图，必须可回放、可验链 |
| 谁改的、基于什么版本（`actor` / `expectedGraphVersion` / 错误码） | 扁平日志 `graph_replanned_by` | 运维事实，不参与状态推导；混进哈希链会让链里出现不该折叠的字段 |

## 四、分段：因为单文件有一条物理上限

`fs.readFileSync` 要建字符串，V8 的 `MAX_STRING_LENGTH` 是 **512 MB**。实测 512 MB 直接 `ERR_STRING_TOO_LONG`，不是变慢，是抛错。

真实 journal 约 **528 B/行** ⇒ **512 MB ≈ 102 万行 ≈ 50 万节点** 就到顶。

### 分段策略与一个刻意的选择

```
journal.jsonl           ← 活动段，**永远叫这个名字**
journal.0001.jsonl      ← 封存段
journal.0002.jsonl
```

**为什么活动段不带段号**，这是有意为之：

| 做法 | 老版本读者的行为 |
|---|---|
| 活动段带段号（`journal.0007.jsonl`） | 只认 `journal.jsonl` → 读到一个**老的封存段**，是个合法前缀 → **安静地少看一半历史** |
| **活动段恒为 `journal.jsonl`** | 滚动后读到的是从中间开始的 `seq` → **`STATE_SEQ_GAP` 响亮失败** |

**「响亮失败」优于「安静地看一半」。** 一个少看一半历史但声称状态正常的系统，比一个直接报错的系统危险得多。

## 五、快照：加速器，不是权威

快照（`snapshot.json`）只是**避免每次都全量重放**的加速器：

- 快照带 `seq` / `version`（内容哈希）/ `graphRevision`；
- 打开时**校验锚点**：快照的 `seq` 与 `version` 必须能和 journal 对上；
- 对不上 → **退回全量重放**，而不是信快照。

所以「删掉快照」永远安全（只是慢一点），「信一个锚点不符的快照」才是灾难。

## 六、CAS 与并发

持久化层用 revision 做 CAS（compare-and-swap）：每次写入带 `expectedRevision`，不匹配就拒。

崩溃可能留下的中间态由**恢复路径**处理，而不是靠「小心别崩」：

```
open() → 验链 → 锚点校验快照 → 通过就用快照+重放，不通过就全量重放
```

## 七、性能：成本不随规模增长

这是最该盯的指标——**单点变快不可信，跨规模持平才可信**：

| 指标 | 实测 |
|---|---|
| 每节点成本（claim + 证据 + 验证 + 心跳） | **6.8 ms** |
| 1000 → 2000 节点 | 比值 **1.01×**（不再随规模增长） |
| 10 万节点冷启动 | **0.087 ms/节点** |
| journal 读取（40000 行窗口，增量） | 全量折叠 3.1 ms → 增量 **0.235 ms** |

### 一个反直觉的实测

在「最近 50 条」的有界选择里，**最小堆反而更慢**：

| 做法 | 68600 条时的耗时 |
|---|---|
| 最小堆 top-k | **11 ms** |
| 环形缓冲 + 单调性探测 | **2.3 ms** |

原因：`at` 字段**近似有序**时，每条新行都真的比堆顶新，每条都要 `siftDown` 六层。**堆适合乱序 top-k，不适合本身近似有序的输入。**

同一处还有个 10× 优化：`dispatchView()` 在 68600 条派发登记上原来 **46 ms → 4.5 ms**，三处原因分别修掉：

1. 失联判定每轮对全部 live 重新解析时间戳并无条件拷贝两个 Map → 时间戳在折叠时算一次（`atMs`），失联判定先扫后拷（无过期项零分配）；
2. `active.rows` 只要最近 50 条却先全量排序 → 环形缓冲 + 单调性探测；
3. 积压与在跑计数各跑一遍全量 `filter` → 合并成一次遍历。

## 八、踩过的坑

**「某条路径的前提在另一条路径里被悄悄破坏」——同一形态在多处出现。** 本章相关的一例：

- `expire()` 只把 `claimed/running` 送回 ready，`submitted` 走空分支 → 租约删了、状态不动。详见 [03 租约与 fencing](03-租约与防重放.md)。

### 残留的锁：上一个进程死了，后面的全在空等 15 秒

做 32 并发标定时撞到的真实情况（[06](06-容量与宿主依赖.md) 那次探针的副产品）：

```
core-state/journal.lock → {"owner":"dsh-l0-control","pid":792,"heartbeatAt":"2026-11-21T10:48:34","ttlMs":1800000}
pid 792                 → 不存在
heartbeat 距今          → 33.6 小时（TTL 只有 30 分钟）
```

于是每次 `persist()` 的返回都是：

```
appended: 0
error: { code: "PERSISTENCE_UNAVAILABLE", message: "[STATE_LOCKED] 等待锁超时（15000ms / 34 次尝试）" }
```

**这是设计，不是 bug**：过期锁不会被悄悄抢占（和「过期租约不会被悄悄续成新 token」是同一条纪律）。代价是运营后果——上一个进程非正常退出之后，**每个写调用都白等 15 秒**再放弃持久化；32 次 spawn 就是 32 次 15 秒。

它同时说明另一件事：**扁平日志 `journal.jsonl` 与 core 状态 `core-state/journal.jsonl` 是两把锁**。那轮 32 次 spawn 的 `agent_spawned` 一条不少写进了扁平日志，而 core 状态 journal 的 mtime 停在一天前——**看到「日志有记录」不等于「状态落盘了」**，这两件事要分开查。

处置：**删锁不够，必须重载插件。** 这一点是实测出来的——把确认 `pid` 已死的锁文件删掉之后，`persist()` 依然报同一条 `STATE_LOCKED / 等待锁超时`。原因在 `service.ts`：

```ts
async persistence(): Promise<CorePersistence | null> {
  if (!this.persistenceRef && !this.persistenceError) {   // ← 失败被记住
    try { this.persistenceRef = await CorePersistence.open({ ... }); }
    catch (error) { this.persistenceError = String(error); }  // ← 之后永不再试
  }
  return this.persistenceRef;
}
```

`persistenceError` 一旦被设上，**这个服务实例生命周期内再也不会重开**。所以正确顺序是：确认 owner pid 已死 → 删锁 → **重载插件或重启宿主**（实测重启后 `persistence.error` 变 `null`，recovery 正常，`restored 608 records`）。

两件该补的事：① 启动时检测 owner pid 已死 → 记 `lock_orphaned` 事件；② `persistence()` 失败后应带退避重试，而不是一次失败终身放弃。
