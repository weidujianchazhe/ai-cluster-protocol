# 02 · 派发与闸门

> **「为什么只派了 3 个」**——这一篇回答的就是这个问题。
> 这是本插件设计密度最高的地方，也是最容易让人误判「是不是坏了」的地方。

## 一、派发是确定性决策，不是某个 Agent 在分配任务

派活循环按 journal 推导出**候选计划**，再用同一份容量快照裁剪。没有「调度 Agent」这个东西——所以可复现、可解释。

两条入口，同一套闸门：

| 入口 | 谁用 | 行为 |
|---|---|---|
| `task_next` / `task_claim` | worker 自己 | 「我该干什么」→ 准入四道闸门 → 发租约 |
| `dispatch` | 协调者 | 定时 tick，生成候选计划 → 每个候选一次 `agent_spawn`。**只出计划，不代领** |

### `role` 是载体职务，`capability` 是工作需求

`task_next({ role })` 的 `role` 是执行载体职务筛选，**不是能力标签匹配器**：

- 节点 `capability` 是已知 worker 职务（`CODE` / `AUDIT_CODE` 等）→ 只匹配同职务；
- 节点 `capability` 是自由字符串（如 `distributed-systems-analysis`）或未设置 → 对所有 worker 可见，谁有能力谁 claim；
- `dispatch` 启动 worker 时，`role` 只定执行载体身份；自由 `capability` 标签会作为能力包传入 worker，不回退丢弃。

这不等于系统已经能验证某个 worker **真的**具备该能力；标签目前是任务需求描述，实际执行能力仍由模型完成。能力标签不会被偷偷当成固定 role。

## 二、闸门是一条优先级链

拦截顺序固定，先命中先停：

```
巡检/防重放  >  预算  >  宿主退避  >  分区满员  >  四道限流（tick / 容量 / 速率 / 排队）
```

**每项跳过都带 `gate` 字段说明是哪一道挡的**，并给出「该调哪个参数」。这不是装饰——见第 5 节的反面案例。

## 三、四道闸门各管一件事，绝不混

| 闸门 | 管什么 | 参数 | 满了怎么办 |
|---|---|---|---|
| **容量** | 同时**在做多少** | `maxParallel` / 分区 `maxActive` | 等 worker 完成 |
| **预算** | 总共**能烧多少** | 全图 / 分区 / 节点 `maxTokens` | 加预算，重试无用 |
| **速率** | **每秒能派多少** | `dispatchRatePerSecond` | 等下一窗口 |
| **排队** | **派出去但没 claim** 能积压多少 | `maxQueuedTasks` | 等 claim 或释放 |

### 为什么「排队」要单独算

因为它**挡的时机不同**：积压的 worker 迟早会同时抵达 claim 层，等到那时才拒，`spawn` 已经烧掉了。所以在派发前就限住。

`maxQueuedTasks = 0` 视为**不限**，不是「一个都派不了」——这是容易配错的语义。

## 四、预算按作用域生效

一个分区烧完自己的额度，**只挡它自己**（以及它的子分区），不会把同图其它分区冻住。

- 父分区是**汇总口径**：父满了，子也不能再超。
- 派活计划与准入用**同一套**预算口径 → 额度已满的节点在计划阶段就跳过，并说明「哪个作用域、已用多少 / 上限多少」，不再「派出去 → 被 claim 拒一次」。

## 五、派发失败按可重试性分流

这是**两类成本不对称**的地方，不能混成一个错误码：

| 类别 | 例子 | 处理 | 理由 |
|---|---|---|---|
| **瞬时**（可重试） | 宿主满载（并发/配额/容量） | 节点保持就绪，下一轮重试 | 会自己变好 |
| **确定性**（不可重试） | preset 不存在、prompt 超长、role 非法 | 记进 `dispatchView().failed`，**停止派发**，改完配置手动派一次才解除 | 每轮都会白烧一次 spawn，并把 journal 刷满同样的错误 |

**无法归因时一律按可重试处理**——因为两边误判的代价不对称：

- 把「可重试」误判成永久失败 → **节点永久卡死**（没人再派它）
- 把「永久失败」误判成可重试 → 只是多派几次

## 六、归因：那个 `gate` 到底多重要

### 反面案例（真实踩过）

四类限流拒绝在顶层**全被压成 `core-failed`**，真码只剩在 `detail.code` 里，而 worker 契约判的是顶层 `error`。于是：

- 「某域满员、换域即可」和「预算耗尽、重试无用」被当成同一个未知码退避；
- 分区满员那一支还会去等**全图**额度，而全图额度根本没满 → 它会一直等到超时，期间那个域一直是空的。

### 现在

拒绝原因**直达顶层与 journal**。并且**局部原因必须给局部建议**：分区满员单独归因，因为若给全局建议，运维会去调 `maxParallel`——**那个参数对这里毫无作用**。

### 重试语义也要分开

| 原因 | 停手后放回可派？ |
|---|---|
| 容量 / 分区 / 速率（瞬时） | ✅ 对 |
| **预算耗尽** | ❌ 不会自己变好。放回可派就是「派一个 → 被拒 → 再放回」无限空转，每轮白烧一次 spawn |

所以预算拒绝进 `failed`（别再派），成功派一次即解除。

## 七、`lastTick` 与 `gateHistory` 是两个问题

| 问题 | 读哪 | 说明 |
|---|---|---|
| 「**最近一轮**被谁挡」 | `lastTick.gates` | 瞬时原因让相邻两轮完全不同，单轮结论会随取样时刻漂移 |
| 「**这段时间**主要卡在哪」 | `gateHistory`（默认 5 分钟窗口，`dispatchGateWindowMs` 可调） | 把窗口内所有轮次的命中累加 |

**「无归因数据」不等于「没被挡」。** 老版本写的、没有 `gates` 字段的 tick 行单列为「无归因数据」，不计入「没被挡」——混进去会让命中率被系统性低估，而低估的方向正好是「看起来一切正常」。

### 实现：增量折叠 + ring

不是每次重扫 journal，而是保留窗口内**逐轮 ring**，聚合只走 ring：

| 场景 | 耗时 |
|---|---|
| 40000 行窗口全量折叠 | 3.1 ms |
| 后续无新行（增量） | **0.235 ms** |

**存 ring 而不是累加值**，是因为滑动窗口必须能真正删掉过期项——只存累加值就删不掉，一小时前的旧原因会永远留在分布里。

## 八、宿主退避：它说等，就真的等

**宿主退避与容量是两件事，必须分开报**：

| 概念 | 谁的限制 | 调本插件参数有用吗 |
|---|---|---|
| **容量** | 我们自己的并发上限 | ✅ 有效 |
| **宿主退避** | 宿主的额度（如 `active child limit`） | ❌ 调什么都没用 |

混成一个「满了」，运维就会去调错的旋钮。宿主退避期间**不尝试**，而不是「试一下被拒再退避」——后者会把 journal 刷满。

宿主的一个坏消息：**`retryAfterMs` 常为 `null`**（不告诉你什么时候恢复），所以退避只能按固定节奏探测，没有依据算「最优等待」。

## 九、派发视图：三个问题的答案在一处

`dispatchView()` 是**只读**的，不触发任何派发或领取：

| 字段 | 回答 |
|---|---|
| `active` | 现在有几个 worker 真在跑（登记仍认为活着） |
| `released` | 上轮为什么允许重派（每个节点一条原因：stale / heartbeat-failed / claim-rejected） |
| `failed` | 哪些节点确定性失败已停派 |
| `rate.usedLastSecond` | 真实 spawn 数（候选 / dryRun 不计） |
| `lastTick.gates` | 上一轮被哪道闸门挡 |
| `gateHistory` | 最近窗口内各闸门累计命中 |

没有这些，前面八个问题都只能翻 journal 手工数——**等于没有可观测性**。
