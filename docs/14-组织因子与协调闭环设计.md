# 14 · 组织因子与协调闭环

> 组织不等于给 agent 排固定职位，也不等于再造一个常驻「总管 Agent」。
> **工作图仍由组成因子按任务生长；协调是图内按需出现的能力与流程。**
>
> 本文是设计稿，区分「当前已实现」与「建议实现」，不把方案冒充成现有功能。
> **本轮已落地第 0 阶段（只读组织审查）与第 2 阶段的 CAS 部分**，落地状态见第九节。

## 一、裁决：需要协调能力，但不需要常驻经理 Agent

**当前工作流程是必要的组织骨架，但还不足以构成完整的组织能力。**

它已经能表达和执行一张成形的工作图：节点、依赖、能力标签、分区、预算、租约、证据和独立审计。但任务执行中发现跨节点冲突后，系统还缺少一条完整的闭环：

```text
冲突/变化被发现
    → 判断影响范围与所需能力
    → 按需形成协调/整合工作
    → 有依据地处理或升级
    → 更新工作图与受影响节点
    → 重新执行并独立验收
```

所以答案不是「再画一棵固定组织树」，也不是「让一个中心 Agent 永远管所有人」，而是：

> **组成因子决定组织需要什么；运行中的事实触发是否需要协调；协调结果回写工作图和证据链。**

## 二、当前已经有什么

当前 `GraphSpec` 已有一组可以构成组织的基础因子：

| 组成因子 | 当前作用 |
|---|---|
| `nodes` / `deps` | 描述工作与先后依赖；上游完成后下游才 ready |
| `capability` | 自由能力需求标签；已知 worker 职务只用于兼容性路由 |
| `writeScopes` | 声明预期写域；目前是 advisory 上下文，**不是文件级锁** |
| `coordination.groups` | 把相关节点归为一组 |
| `coordination.partitions` | 划分局部工作域，并能约束并行与预算 |
| `coordination.delegation` | 表达委派深度、扇出、幂等等边界 |
| `coordination.aggregation` | 表达聚合完成策略（all / any / quorum） |
| 租约 / fencing / journal | 控制节点写入归属、阻止旧载体提交、记录状态顺序 |
| evidence / 独立审计 | 让节点完成有证据支撑，并由其他实例审计 |

另有 `facets.ts` 的组织视角（当前主要汇总分配、依赖和过载信号），`conflict.ts` 能从 facet 摘要检测若干结构性冲突并按能力路由，`replan.ts` 能以事务方式增删非终态节点并递增图版本。

## 三、缺口：基础件曾经存在但闭环没接通（本轮已接通第 0 阶段）

以下是**接通前**的源码调用关系现状，不是对设计意图的推测。第 2、3 条已在本轮修掉，保留原文以便对照：

1. `coordinatorTick` 当前做过期租约回收与超时审计派发，**不负责通用的跨节点语义裁决**。
2. ~~`buildClusterState` 会调用 facet 与冲突检测，生成冲突摘要和 next actions；但当前生产源码里没有服务/协调器调用它的路径。~~ → **已接通**：`organization_review` 经 `core.organizationStatus` 调 `buildClusterState`，并把集成契约与写域重叠一并投影出来。
3. ~~`replan` 核心函数存在，也有自检覆盖；当前生产源码里没有调用它的服务工具路径，因此冲突检测结果不会自动触发重规划。~~ → **已接成显式工具** `graph_replan`（强制 `expectedGraphVersion` CAS）。**仍然不自动触发**：冲突只出草案，采纳由调用方决定。
4. `writeScopes` 会传入任务说明/worker 上下文，但**不阻止文件系统写入**。节点租约锁的是节点，不是文件。→ 现在还会随 budget 落到 `NodeRecord`，于是「并行写域重叠」**能算出来**（但依然只是声明，不是锁）。
5. `conflict.ts` 现有检测对象是 facet 摘要中的结构信号；它**不比较两个节点产物的接口、字段或语义**。
6. 协调结果还没有统一的记录格式来表达「冲突是什么、由谁处理、依据哪条证据、哪些下游结论因此失效」。→ 现在有 `signals[].basis` + `proposals[].replanDraft` + `graph_replanned.rewired`，但「哪些下游结论因此失效」仍是**未解决项**（只给了 `rewired` 的旧/新依赖，没有自动作废旧证据）。

因此，当前系统能执行**预先组织好的工作**，也能**发现并起草**工作变化；它还不能可靠地自行裁决并自动恢复。

## 四、组织能力应该落在哪儿

### 1. 组成因子：声明组织意图，不手绘组织层级

工作图的生成者仍按任务拆解节点和依赖。组织因子描述的是**边界与协调需求**，不是「必须有一个经理、两个组长、五个专家」这样的固定编制。

建议逐步补齐四类声明：

| 因子 | 要回答的问题 | 当前基础 |
|---|---|---|
| **职责边界** | 每个节点负责什么、不负责什么？ | `node.spec`、acceptance、`writeScopes`（目前 advisory） |
| **共享契约** | 多节点共用什么接口、数据结构、交付格式？ | 当前多在节点 spec 中自由描述，缺少统一的契约产物引用 |
| **集成点** | 哪些节点完成后必须做跨节点整合？ | 可用 `deps` / aggregation 表达，但目前没有统一的 integration 语义 |
| **冲突策略** | 哪类冲突自动检查、哪类路由给能力节点、哪类必须升级给人？ | `conflict.ts` 有 needs 路由基础，缺少端到端处置策略 |

**不应默认增加这些因子**：如果任务没有共享接口、跨节点契约或整合需求，不应为了「组织完整」而机械插入协调节点。

### 2. 运行流程：检测后按需形成临时组织

```text
组成因子 + 愿望
       ↓
按任务生成工作图（没有预设树形编制）
       ↓
节点执行、证据提交、独立审计
       ↓
检测到达到触发条件的跨节点问题
       ↓
按需生成协调/契约/集成节点，或路由给既有能力节点
       ↓
决策留证据；必要时受约束地 replan
       ↓
重做受影响节点 → 独立审计 → 恢复下游派发
```

这里的「组织涌现」是**从任务结构与运行信号生成有边界的临时组织**，不是任意自发扩权，也不是宣称集群产生了意识。

## 五、触发协调的信号

第一版不需要复杂预测模型。优先使用可解释、可回放的信号：

| 信号 | 例子 | 建议动作 |
|---|---|---|
| **共享写域重叠** | 两个并行节点都声明修改 `src/api/` | 暂停冲突范围的并行，生成所有权/接口协调项；注意当前 writeScopes 只声明，尚非强制锁 |
| **契约不一致** | 两个产物对同一 API 的字段名、类型或版本有冲突 | 创建 integration/contract review 节点，要求引用两边产物并产出统一契约 |
| **上游假设变化** | 已完成的上游契约被修订 | 标出依赖该契约的下游节点，按影响关系决定重验或重做；不能只改上游后仍把旧下游当有效 |
| **重复劳动** | 两个节点 acceptance、产物范围高度重叠 | 报告重叠并要求合并、拆分或说明独立理由，不自动删任一结果 |
| **反复业务失败** | 同一节点多次因真实验收失败被拒 | 创建诊断/需求复核节点，区分业务失败与系统重试；避免无限重派同一方案 |
| **机器证据冲突** | 同一验收条件出现不一致验证结果 | 由独立验证器复核；记录输入、验证器版本和判定证据 |

不得把「facet 有一条 note」直接等同于「冲突已裁决」。**发现、路由、裁决、重规划是不同状态**，每一步要可见。

## 六、协调与裁决的权责

### 协调服务不是总管 Agent

协调器可以作为**确定性控制面服务**，负责：扫描触发条件、去重、限额、生成协调待办、把有依据的变更送入 replan。它不应凭一句 LLM 判断就暗改节点、预算或权限。

具体分析可以由工作图按需生成的临时节点完成。临时组织节点也是普通图节点：有目标、写域、验收条件、租约、证据和独立审计；做完后不成为永久身份或固定管理层。

### 裁决分路

| 冲突类型 | 处理者 | 约束 |
|---|---|---|
| 确定性的结构问题（悬空依赖、非法图变更） | 规则/校验器 | 直接拒绝，给出可定位错误 |
| 技术契约 / 接口 / 证据矛盾 | 相应能力的临时协调或审计节点 | 不由冲突双方自行给自己盖章；结果要附双边证据和验收条件 |
| 使用体验 / 价值取舍 | 人类 | 不伪装成 agent 能客观决定的技术事实 |
| 当前没有承接能力 | 明确列能力缺口，等待补能力或人处理 | 不静默回退到 CODE 或任意默认角色 |

**共同主体不等于无审计**：实例可以承载集群所需的主权限；但每次高影响组织变更仍需记录「哪个实例执行、基于什么证据、改了哪些节点」，并由独立实例验证结果。这里保护的是可追溯性与一致性，不是把实例变成互不信任的永久角色。

## 七、replan 安全边界

现有 `replan` 已支持单事务增删节点、递增 `graph_version`、写 `graph_replanned` 事件，并拒绝删除终态节点。把它接到协调闭环前，还要规定：

1. **提议与执行可追溯**：冲突报告引用原节点、产物/evidence、冲突类型与拟议动作。
2. **幂等与并发保护**：携带预期 `graph_version` / 幂等键；旧版本提议不得覆盖新图。
3. **影响范围显式化**：上游契约变化时列出受影响的下游节点；旧证据不能默认为仍适用。
4. **终态保护不绕过**：已有 replan 不得删除 `done` 节点；如结论过期，应新增修订节点或显式 supersede 关系，而不是改写历史。
5. **次数与成本有上限**：每个冲突限定协调轮次、节点数、并发和 token 预算；达上限就停下并报告。
6. **不得把失败伪装成解决**：无能力、无共识或证据不足时状态应是待人/待能力，不应自动标记通过。

## 八、实施顺序：先闭环最小链，不做全知管理器

| 阶段 | 工作 | 验收标准 | 状态 |
|---|---|---|---|
| **0. 设计与只读观测** | 把当前 conflict/state projection 公开为组织审查结果；显示冲突、影响节点、缺失能力 | 同一 journal 重放出同一报告；不派活、不改图 | ✅ 本轮完成（`organization_review`，`fingerprint` 可回放，只读性有断言） |
| **1. 人工确认的协调节点** | 对高置信触发生成临时协调/集成节点，由活集群实例接手；决策写 evidence | 能证明冲突发现→处理节点→独立验收完整可回放 | ⏳ 只出草案（`proposals[].replanDraft`），**不自动建节点** |
| **2. 受约束自动 replan** | 仅对确定性规则允许的结构动作自动改图；语义裁决仍走专门审计/人类路线 | 版本 CAS、幂等、影响范围、预算上限都有测试 | 🟡 机制齐了（`graph_replan` + `expectedGraphVersion` CAS + 前置结构校验），**尚未自动触发**；预算上限未接到协调轮次 |
| **3. 再评估组织策略** | 以返工、冲突关闭时间、重复工作、集成失败、成本衡量效果 | 对照数据证明收益大于协调开销后才扩大自动化 | ⏳ 未做（没有数据，不宣称收益） |

**不要先做**：固定金字塔角色树、常驻总经理 Agent、自动覆盖冲突结果、或者没有成本上限的递归扩图。

## 九、结论与落地状态

- **组织应该融入组成因子与流程**；现有工作图因子已经提供节点/依赖/分区/委派/聚合基础，本轮补上了**跨节点契约（`integrationContracts`）**、**冲突触发（`signals`）** 与**可回放的协调草案（`proposals`）**。
- **需要管理/协调功能，不需要固定的管理者身份**。确定性协调服务守规则，临时协调节点解决具体问题，独立审计验证结果。
- **先实现「能发现、能形成协调待办、能留下可回放裁决」**，再讨论自动重规划；不要一步跳到「集群自己会组织好一切」。
- 整体方案会提高复杂工程的可组织上限，但增加协调节点、审计和返工成本；它不是性能优化，也不保证省 token。

### 本轮实际接通了什么

| 能力 | 落地位置 | 机器判据 |
|---|---|---|
| 集成契约因子 | `graphspec.ts` `OrganizationSpec.integrationContracts` | 五种非法写法在 `planGraph` 阶段被拒 |
| 组织审查（只读） | `core/organization.ts` + 工具 `organization_review` | `verify-organization` 组 1–5：只读性、`fingerprint` 可回放、写域重叠 |
| 受约束改图 | `core/replan.ts` + 工具 `graph_replan` | 组 6–11：`replan_stale_graph` 零写入、终态保护、自依赖/悬空/成环、`rewired` 留痕 |
| 写域声明落地 | `commitGraph` / `replan` 把 `writeScopes` 写进 `NodeRecord.budget` | 组 5：不落图就算不出重叠（旧实现落图即丢） |

### 仍然明确没做的

- 语义裁决（两个产物接口到底谁对）——不在这一层做，交临时协调/审计节点或人。
- 自动触发 replan——冲突只出草案，采纳是显式动作。
- 协调轮次/节点数/token 的**上限执行**——设计已写，代码未接。
- 上游契约变化后**自动作废下游旧证据**——只给了 `rewired` 的新旧依赖，作废仍是人/协调节点的事。
- 「协作/协调到底有没有用」的对照数据——`delta` 仍算不出来。
