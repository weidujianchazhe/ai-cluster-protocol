# A2 · 已知问题与待办

> **附录编号**：`A1`/`A2` 不占正文 `01`–`14` 的递归序列——正文讲「怎么运作」，附录放「猜想」与「已知问题台账」。

> **这是问题台账，不是缺陷清单。** 只记「已经知道、但故意先不修」的东西。
>
> 收录标准：**能复查**（说得清现象和复现入口），**有明确的影响面**（会不会影响插件功能），**有修复的触发条件**（什么情况下必须动手）。说不清现象的进不来——含糊的抱怨没法验证，也没法验收。
>
> 不收：待实现的新能力（那是设计文档的事）、已修的问题（那是 commit 和报告的事）。

## K-01 · 面板侧的显示毛病

**已知**：用户反馈「插件面板侧有点毛病」，但未给出具体现象（哪一屏、什么情况下、期望与实际差在哪）。

**为什么不急着修**：
- 不影响插件功能——面板是**只读投影**，投影错了不会让图错、不会让验收错；
- 现象未具体化，动手修等于赌。**先等一次可复现的观察**，比猜着改更省事。

**它该被修的信号**（任一出现就升级）：
1. 显示的错误会让人**做出错误决策**（例如把"未运行"看成"正在运行"，从而误判能不能再派活）；
2. 面板读到的是**陈旧状态却没标陈旧**——这条最危险，因为它会伪装成事实；
3. 有人开始绕过面板直接查 journal「因为面板不可信」。

**下次复现时请记三件事**：哪一屏、当时的 `graph_status` 摘要、期望看到什么。

> 备注：面板侧车（`src/ui-server.ts`）读的是 `uiSnapshot`，与 `graph_status` 同源；若两者不一致，那本身就是一个明确的可查线索（说明投影层有分叉），比"面板有点毛病"更能定位。

## K-02 · 千级 Agent 的可视化不便

这条不是"某个控件坏了"，而是**当前面板的交互形态是按「几十个节点」设计的**，一千个节点时它会变成"能打开但没法看"。

**具体的机制瓶颈**（都在代码里，不是感觉）：

| 瓶颈 | 位置 | 千级时的表现 |
|---|---|---|
| 节点分页默认 50、上限 500 | `graph_status({limit, offset})` | 1000 节点要翻 20 页；没有"按 stage / 按状态 / 按分区"的聚合入口 |
| 在跑行只留最近 50 条 | `dispatchView().active.rows`，超出标 `truncated` | 想看"哪 300 个在跑"看不到，只看到尾部 50 条 |
| 闸门历史是环缓冲 | `gateHistory`（窗口内累计） | 只能回答"这段时间主要卡在哪"，不能回答"第 3 分钟那一波是谁挡的" |
| 邻域摘要按 `maxNeighbors` 截断 | `neighbor_digest` / `organization_review.next` | 千级时永远是"截断视图"，且 `caveatFlags` 会一直挂着 `truncated` |
| 工作区只读侧车 | `src/ui-server.ts`（`/l0-control/*`） | 没有游标/增量协议，面板要么全量要么没有 |

**为什么不急着做**：
- 插件本身的运行不依赖面板。真要看全局，`graph_export` 导出的投影 + journal 是权威且完整的；
- 千级协作任务**本身还没实跑过**（见 [06](06-容量与宿主依赖.md)：32 稳、54 就已经把宿主 inspector 打崩）。**先解决能不能跑到 256，再谈 256 好看不好看**——反过来做是给一个跑不起来的东西做仪表盘。

**如果要做，方向已经清楚**（记下来免得重复推演）：
1. **先聚合、后明细**：面板首屏只给 `counts by stage / status / capability / partition`，点进去才拉明细；一千个节点的高层状态用几百个字符就能说清。
2. **服务端游标而不是全量**：`active.rows` 之类改成 `(cursor, limit)` 增量协议，面板虚拟滚动；截断要给出"还有多少条"而不只是标 `truncated`。
3. **异常优先**：千级下默认只显示"有问题的"（阻塞、租约过期、卡在 submitted、证据 `unknown`），正常的折叠成计数——这和 [12 编排感知](12-agent节点编排感知.md) 里"正常的不占字符"是同一条原则。
4. **导出兜底**：面板永远提供"把当前视图导出成文件"，复杂分析走离线工具（`tools/analyze-session.mjs` 已有先例）。

**触发条件**（满足其一就必须做）：
- 真跑到 200+ 并发，且有人需要**同时**看这些节点的状态；
- 出现"因为看不全而漏掉一个卡住的节点"这类事故；
- 上游 inspector 崩溃修好、并发爬过 128（那时面板会成为下一个瓶颈）。

### 2026-11-27 缓解：**接管官方「子智能体」那一格**，排序改成「在干活优先」

实测数据：本对话根会话下 **210 个子会话**（宿主 `subagents.listDescendants` 口径）。
官方那格按创建顺序平铺，186/210 条时要肉眼找"谁在跑"——所以**直接替换那一格**，
不是另加一个。

| 项 | 做法 |
|---|---|
| 位置 | `conversation.session.header.actions` 的 `id: subagent-catalog`（**同 id = 替换官方那一格**） |
| 排序 | `running` 置顶 → 深度浅 → 名字（后端排好，前端只渲染） |
| 标题 | `在跑 N · 空闲 M · 外部 K` |
| 展开 | 默认 12 条，超过给「展开全部 N」 |
| 刷新 | 10s 轮询；侧车 stale-while-revalidate（见下） |

**信息取舍（必须写清，否则下一个人以为丢数据了）**：宿主 `SubagentCatalogRow` 只有
`id / activity / mode / label / name / hasChildren / parentId / depth`——**没有 token 和耗时**。
官方那格的 `2.4M tok / 5分26秒` 是宿主 UI 自己从会话统计里算的，插件侧拿不到。
所以替换后：**排序和置顶有了，token/耗时没了**。这不是丢，是宿主没暴露。

另外官方那格的 `118 已完成 · 66 未运行` 把 `inactive` 拆成两类（按有没有跑完过），
这需要会话完成态；我们只有 `running / inactive`，所以标题给的是「在跑 / 空闲 / 外部」。

**为什么敢接管**：slot 文档写明「reusing a shipped id puts you in THAT cell and replaces it」，
且那格 `replaceRisk: none`（list 型）。风险是宿主升级后语义变化——所以接管实现刻意保持薄：
只依赖 `/ui/subagents` 一个数据源，不碰官方内部组件。

**性能坑（重要）**：`subagents.listDescendants` 在 210 个子会话上实测 **15–18 秒**。
直接给面板轮询会堆积请求，所以侧车做了 stale-while-revalidate：
首次冷读慢（或超时返 `stale`），之后每次 **~2ms** 返回缓存，后台每 30s 刷新一次。
返回里必须看 `cacheAgeMs` / `stale`——**数据可能是旧的，面板不能假装它是最新的**
（列表底部会显示「数据可能不是最新的（Ns 前）」）。

### 单一开关：插件的协作状态跟随宿主

**问题**：宿主有「启用智能体团队协作」（`agentTeams.isEnabled` / `setEnabled`），
插件原本也有一套 per-session `coordination`（journal `access_changed`）。
两套并存 = 迟早对不上，而且面板上会出现两个开关。

**做法**：插件不再自己说了算。

| 层 | 现在谁定 |
|---|---|
| 协作开关（UI） | **只有宿主那一个**。插件的 `l0-coordination` 已撤，slot 里只剩 `agent-team` |
| 协作状态（判定） | `isSessionEnabled()` **读宿主 `agentTeams.isEnabled`**；宿主没这个能力时才退回本地 journal |
| `/ui/access` 返回值 | 带 `teamMode`（宿主值）与 `source: 'host' \| 'journal'`——**说清这个 `enabled` 是谁给的** |
| 面板「启用」按钮 | 调 `/ui/team-mode` → `agentTeams.setEnabled`，拨的就是宿主那个开关 |

实测：`{"enabled": true, "teamMode": true, "source": "host"}`。

**一个必须记住的坑**：`isEnabled(caller)` 要**真 Agent**。传 `{ id }` 这种假对象会抛错，
第一次就把它读成了 `null`（于是 `source` 变成 `journal`，看着像"宿主没这能力"）。
同步路径要用 `agents.get(sessionId)` 取活 Agent——`sessionController.resolveAgent` 是异步的，
在同步的 `accessFor()` 里用不了。

## K-03 · 宿主 `agentTeams` 契约随 nightly 变化

**现象**（2026-11-27 实测，非推测）：

```
team_status → { ok: false, error: "projection-failed",
                detail: { name: "TypeError", message: "teams.membership is not a function" } }
```

宿主 `agentTeams` 原本有 11 个方法（`membership` / `listMembers` / `spawnTeammate` /
`sendMessage` / `createTask` / `getTask` / `listTasks` / `updateTask` / `waitForChange` / `interrupt`…），
更新后只剩 **6 个**：

```
isEnabled / setEnabled / createTask / getTask / listTasks / updateTask
```

**影响面（这条是真的影响功能，不是显示）**：

| 丢失的能力 | 后果 |
|---|---|
| `spawnTeammate` | `agent_spawn` 只能走 activation，返回 `ownerCapable:false` + `teamPathBlocked:'host-method-removed'`；**实例不能作 TeamTask owner** |
| `membership` / `listMembers` | `team_status` 的成员名单恒为空（旧代码直接 `TypeError`，整个工具报错） |
| `sendMessage` | 给 Team member 投消息退化为 `subagents.sendMessage` 路径 |

**已做的适配**：
1. `team_status` 加能力探测，缺方法就**退化**（最小 membership + 空名单 + `capabilities.*=false`），
   不再把「宿主变了」伪装成「插件报错」；
2. `agent_spawn` 的降级原因显式写进返回（`teamPathBlocked`），不再让 `ownerCapable:false` 自己解释自己；
3. `env_check` 的 `hostServices.teamCapabilities` 逐项列出缺什么、影响什么；
4. 新增 `team_status.teamMode`，读宿主 `isEnabled`——**这一项在新契约里还在**。

**为什么没「修好」**：`spawnTeammate` 是宿主不给，插件造不出来。要恢复 TeamTask owner 能力，
只能等宿主把方法补回，或者改用团队板的投影口径（`board_task_*`）。

**下次升级 DSH 时先跑这个**：`team_status`，看 `capabilities` 里哪项变成 `false`。
